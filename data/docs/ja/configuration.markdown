運用者が設定するものはすべて、メールと並んでデータベースに置かれます。サーバーは起動時にそれを読み、以後は数秒ごとに読み直すので、ダッシュボードでの変更も、別のインスタンスからの変更も、再起動なしに効きます。

設定ファイルはありません。サーバーはかつて `teanode.yaml` で記述されていました。それをデータベースに移したことが、複数のインスタンスが、どのドメインが存在しどの資格情報が有効かで食い違うことなく一緒に動ける理由です。

そこに置けないものが二つあり、環境変数から来ます。データベースにどう届くか、そしてこのプロセスがどのインスタンスか、です。

## 環境変数

出発点はこれで書き出せます。

    teanode-server config env --output .env \
      --hostname mail.example.com --domain example.com

ひとつの変数は必須です。

**`TEANODE_DATABASE_URL`**――設定、メール、カウンターが置かれる場所。例えば `postgres://teanode:password@postgres:5432/teanode?sslmode=disable`。個別の `TEANODE_DATABASE_HOST`、`TEANODE_DATABASE_PORT`、`TEANODE_DATABASE_USER`、`TEANODE_DATABASE_PASSWORD`、`TEANODE_DATABASE_NAME`、`TEANODE_DATABASE_SSL_MODE`、`TEANODE_DATABASE_LOG_QUERIES` は項目ごとに上書きします。既定のホストはありません。あれば、変数の抜けたインスタンスが空のローカルデータベースに繋がり、自分を新品のサーバーだと判断して自分を設定してしまい、それが成功に見えるからです。

三つは任意です。最初のものはインスタンスが複数になってから意味を持ちます。

**`TEANODE_INSTANCE_ID`**――同じデータベースを共有する他のプロセスからこのプロセスを区別します。使用量カウンターを増やすときのキーの一部で、増分は行を読んで書き戻す形なので、同じ名前を共有する二つのインスタンスは互いの数を失います。既定はホスト名で、コンテナにはすでにあります。32 文字を超えれば末尾の 32 文字に切り詰めます。

**`TEANODE_UPGRADE_DIRECTORY`**――ダッシュボードからインストールした更新が、動いているバイナリを上書きできないときに新しいものを置く場所であり、次の起動がそれを探す場所です。`TEANODE_SERVER_DATA_DIRECTORY` が設定されていればその下の `upgrade` が既定で、そうでなければ空です。空のとき、自分の実行ファイルを置き換えられないデプロイは、自分で更新できないと告げられます。絶対パスでなければならず、相対パスは解決されずに拒否されます。ステージされたバイナリは、どの作業ディレクトリから始まった起動にも見つかる必要があるからです。

これが設定ではなく変数である理由はひとつです。ステージされたバイナリは何かがデータベースを開く前に見つかって実行されなければなりません。このプログラムは知らないマイグレーションを戻すので、先にデータベースに触れた古いバイナリは新しいリリースのスキーマを取り消してしまいます。設定はデータベースにあります。これはそこに置けません。

コンテナでは、マウントしたボリューム上のディレクトリであるべきです。同梱の `docker-compose.yml` は `/var/lib/teanode/upgrade` を指定します。イメージ内のディレクトリはコンテナが作り直されるまでは動き、その後は黙って古いバイナリに戻ります。このディレクトリはサーバーを動かすユーザーだけが触れるように作られ、他の誰かが書けたかもしれないステージ済みバイナリは、次の起動で実行されず拒否されます。

**`TEANODE_ALLOW_MIGRATION_REVERT`**――古いバイナリが、新しいリリースが適用したマイグレーションを取り消すことを許します。既定はオフで、面白いのは既定のほうです。知らないマイグレーションを見つけた起動は、それを戻すのではなく実行を拒みます。戻すと、そのマイグレーションが加えた列とその中身がすべて消え、ここに至る三つのよくある道はどれも偶然だからです。[`docs/coding/database-migrations.md`](https://github.com/ziyan/teanode/blob/main/docs/coding/database-migrations.md) を参照してください。意図してダウングレードするときは `true` に設定します。

## 既存のサーバーを移す

`teanode.yaml` で動いていたデプロイは、それを一度読み込みます。

    teanode-server config import --file /opt/teanode/teanode.yaml

すべてがそのまま持ち込まれます。ドメインとエイリアスの識別子、署名鍵、サーバーシークレット、セッション鍵。どれかを変えれば動いているものが壊れるからです。先にサーバーを止めてください。まだ確認中の設定の半分を採用されないように。`--dry-run` は何が読み込まれるかを告げ、何も書きません。

逆方向は同じ形式のバックアップになります。

    teanode-server config export --file backup.yaml

## 再起動が要る設定

リスナー、TLS、オブジェクトストレージ、データディレクトリ、任意の連携は、プロセスが必要なものを組み立てるときに一度だけ読まれます。これらを変えても変更が保存されるだけで、インスタンスが再起動するまで他には何も起きません。

各インスタンスはそれに気づいて告げます。ログで、そしてダッシュボードの **設定 → サーバー** ページで。そこは古くなった設定を一覧し、再起動を提供します。再起動とはプロセスが終了し、監督しているものが新しいプロセスを始めることです。その場での再起動はありません。それらを組み立て直すことが目的だからです。受け取ったメールはディスクにあり、後で配送されます。その数秒間に接続しようとした送信者は再試行します。

そのページは、何がプロセスを再び始めると考えているかも言います。コンテナ、systemd、あるいは見えない何か。これは推測です。コンテナの再起動ポリシーも unit の `Restart=` もプロセスの中からは読めないので、戻ってくると約束するのではなく監督者が何かを言い、警告に寄せます。

再起動はコマンドでもあるので、デプロイはブラウザーなしで行えます。

    teanode server restart

## 読み、確かめる

    teanode-server config show                 # シークレットは伏せられる
    teanode-server config show --show-secrets
    teanode-server config validate

これらはサーバーが読むのと同じ環境変数を読むので、サーバーが動く場所で実行します。そのコンテナの中か、その env ファイルとともに。それ以外の場所では、クライアントが API を通じて同じ設定を読み書きします。連携は `teanode settings show`、ドメインは `teanode domain list`、といった具合です。[`docs/reference/command-line.md`](/doc/command-line) を参照してください。

## セッションとトークン

どちらも設定ではありません。どちらもデータベースの行で、メールと並んでいます。`session` はサインインしているブラウザー、`token` はこのツールがどこか別の場所からサーバーを管理するための API トークンです。

クッキーとトークンは同じ形です。識別子、シークレット、両方に対する署名。保存されるのはシークレットのハッシュだけなので、データベースのコピーは使えるログインの集合ではありません。署名する鍵は異なります。セッションは `session.key`、トークンは `server.secret`。そのため `session.key` の交換は今まで通り、サーバー上のすべてのアカウントのすべてのセッションを終わらせる非常手段であり、トークンには触れません。

どちらも最後に使われた時刻と場所を、毎分一回まで記録します。リクエストごとにデータベースへ書かずにダッシュボードが表示できるように。失効したものは三十日間、失効と印を付けて残り、一覧が何が起きたかを言えるようにします。毎時の掃除がそれらと、とうに期限切れのものを取り除きます。

各アカウントは自分のものを管理します。`teanode auth login` はダッシュボードを通じてひとつを発行し、頼んだマシン上にプロファイルとして保存します。コンソールは例外です。サーバーシークレットから作ったトークンで認証し、アカウントではまったくないので、ブラウザーなしで最初のトークンを得るには `teanode token create --user ziyan laptop` を使います。

## シークレット

`server.secret`、`session.key`、DKIM 秘密鍵、ACME アカウント鍵、AWS 資格情報はすべて、他のものと一緒に保存されます。サーバーを移す前に、二つは理解しておく価値があります。

- **`server.secret`** はすべての SMTP 資格情報のパスワードに署名します。新しいデータベースに持っていかなければ、設定したどのデバイスも送れなくなります。
- **`session.key`** はダッシュボードのクッキーに署名します。失えば全員がサインアウトされ、それだけです。

どちらも初回起動で生成され、再生成されることはありません。同じデータベースに対して起動した二つ目のインスタンスは、自分で作らずにそれらを採用します。

API はどれも返しません。シークレットを持つ項目は出力で伏せられるので、完全な権限を持つトークンでも読み戻せません。`config export` はそれらを平文で書きます。省いたバックアップは使えるサーバーを復元できないからです。書き出すファイルはあなただけが読めます。

## パス

相対パスは `server.dataDirectory` を基準に解決され、これは絶対パスでなければなりません。かつては相対でもよく、`teanode.yaml` のあるディレクトリを基準に解決されていました。ファイルがなければ基準にするものがなく、相対パスは各プロセスがたまたま始まった場所に落ちてしまいます。

## リファレンス

### `server`

**`name`**――SMTP の挨拶で名乗る名前で、送信時の HELO 名にもなります。例えば "mail.example.com"。このホストに解決しなければならず、逆引き DNS も一致すべきです。そうでなければ受信側サーバーはここからのメールを信用しません。

**`dataDirectory`**――DataDirectory は、サーバーが書くもののうちデータベースにないすべてを保持します。鍵、証明書、メールバッファ、サーバーシークレット。このファイルの他の場所の相対パスはこれを基準に解決されます。

**`logLevel`**――LogLevel は DEBUG、INFO、NOTICE、WARNING、ERROR、CRITICAL のいずれかです。

**`logDirectory`**――LogDirectory を設定すると、受け取ったすべてのメールの .eml コピーを受け取ります。デバッグに便利で、際限なく増えます。

**`secret`**――Secret は送信メールのバウンス返信経路と、SMTP 資格情報の鍵から導かれるパスワードに署名します。初回に生成されます。変えればすべての SMTP パスワードが無効になり、途中のメールのバウンスは行き場を失うので、サーバーを新しいマシンに移すときは一緒に持っていく必要があります。

**`mailServers`**――MailServers は各ドメインの MX レコードに公開するホストで、優先順です。任意で、空なら MX レコードはこのサーバーを指し、ほとんどの人が動かす単一ホストのデプロイではそれが正しい答えです。これらのドメインのメールが複数の名前に届くときに設定します。同じホストを指す mx1 と mx2 の組はよくあり、すべてのドメインが DNS を変えずに移行できる先を提供します。ダッシュボードはそれから各ドメインに、名前ごとに MX レコードを、与えられた順に優先度 10、20、と公開するよう求めます。これらはメールが届く名前です。tls.hosts、つまりこのサーバーが証明書を持つ名前とは無関係です。

### `sso`

パスワードとパスキーの隣に、ID プロバイダーによるサインインを置きます。OpenID Connect のみ。意味のあるプロバイダーはどれもこれを話します。プロバイダーごとにサインインページのボタンがひとつ増えます。プロバイダーに登録するリダイレクト URL は `https://<web ホスト>/api/v1/sso/<id>/callback` です。

**`providers`**――提供する ID プロバイダー。ひとつにつきボタンひとつ。空のリストはシングルサインオンなしを意味します。

### `sso.providers[]`

**`id`**――サインインのパスと各人の identity 行でこのプロバイダーを名指します。小文字、数字、ダッシュで最大 32 文字、そして安定していること。プロバイダーの名前を変えると、その下のすべての identity が孤児になります。

**`name`**――サインインボタンに表示される名前。

**`issuer`**――OpenID Connect の issuer URL。`https` のみ。プロバイダーの設定は `<issuer>/.well-known/openid-configuration` から読まれ、同じ issuer を名乗っていなければなりません。プライベートアドレスは拒否されます。

**`clientId`**――プロバイダーがこのサーバーに発行した client id。

**`clientSecret`**――それに対応する client secret。シークレットなので伏せて表示され、設定の更新で空のままなら保持されます。

**`groupsClaim`**――その人のグループ名を運ぶクレーム。ここの各グループの `idpGroup` と照合されます。空なら `groups`。人は、クレームされた名前を持つすべてのグループに入れられ、もはやクレームされていない名前を持つすべてのグループから外されます。`idpGroup` のないグループは決して触られません。

**`createUsers`**――ここにアカウントのない人がサインインしたときに作るかどうか。パスワードなし、プロバイダーに結び付いた identity、Personal メールボックス、そしてクレームが名指すグループが与えられます。オフなら、このプロバイダーの identity をすでに持つアカウントの人だけがこれでサインインできます。

### `listen`

**`smtpIncoming`**――SMTPIncoming はインターネットからメールを受け取ります。本番ではポート 25。

**`smtpOutgoing`**――SMTPOutgoing はあなた自身のデバイスから、認証済みメールを中継のために受け取ります。本番ではポート 587。

**`imap`**――IMAP はメールボックスをメールプログラムに提供します。サインインの前に STARTTLS が必須です。本番ではポート 143。空にすると無効になります。

**`imaps`**――IMAPS は最初のバイトから TLS で同じものを提供します。本番ではポート 993 で、ほとんどのメールプログラムが最初に試すのがこれです。空にすると無効になります。

**`http`**――HTTP はダッシュボードを提供し、ACME の http-01 チャレンジに答えます。tls.acme.challenge が http-01 のとき、ポート 80 はインターネットから届く必要があります。

**`https`**――HTTPS は TLS でダッシュボードを提供します。

**`debug`**――Debug を設定すると Go の pprof エンドポイントを提供します。localhost にだけバインドしてください。

### `tls`

**`hosts`**――証明書を取得するホスト名。最初のものが主名です。

**`certificateFile`**――CertificateFile と PrivateKeyFile は自分で管理する PEM ファイルを指します。両方が設定されていれば ACME は使われません。

**`privateKeyFile`**――前の項目を参照。両方を一緒に設定します。

**`acme`**――ACME は Let's Encrypt などの ACME プロバイダーから自動で証明書を取得します。

### `tls.acme`

**`enabled`**――前の項目を参照。両方を一緒に設定します。

**`email`**――Email は ACME プロバイダーに登録する連絡先で、期限切れの警告を受け取ります。

**`directoryUrl`**――DirectoryURL は ACME プロバイダーです。テスト時はレート制限に当たらないよう Let's Encrypt のステージングディレクトリを指してください。

**`challenge`**――Challenge はドメインの支配を証明する方法です。"http-01" はポート 80 が、"tls-alpn-01" はポート 443 が届く必要があり、"dns-01" は下の DNS プロバイダーが要り、ワイルドカード証明書を得る唯一の方法です。

**`perDomain`**――PerDomain は各ドメイン自身のメールサーバー名について、サーバー自身の名前とは別に証明書を取得します。それなしでは、すべてのドメインにサーバーの証明書が提示され、送信者が求めなかったドメインが書かれています。既定はオフで、サーバーの更新が、誰も決めていないのに受け持つすべてのドメインの証明書を認証局に求め始めないためです。

**`accountKey`**――AccountKey は認証局に対してこのサーバーを識別します。初回使用時に生成され、他の鍵とともにここに保存されます。失えば再登録で、動きはしますがレート制限を消費します。

**`certificate`**――Certificate と PrivateKey は発行された証明書を PEM で保持します。更新がここに書くので、エクスポートした設定は完全に動くサーバーです。別の場所で復元しても、認証局にもう一枚求めてレート制限を消費するのではなく、証明書を保ちます。これは上の tls.certificateFile とは逆の選択で、理由は次の通りです。これらはこのサーバーが書き、他の何も読みません。一方、自分で管理する証明書は別の何かが書き、それが置いた場所に留まる必要があります。

**`privateKey`**――前の項目を参照。両方を一緒に設定します。

**`route53`**――Route53 は AWS のホストゾーンで dns-01 チャレンジを解きます。

### `tls.acme.route53`

**`enabled`**――前の項目を参照。両方を一緒に設定します。

**`zoneId`**――ZoneID は tls.hosts のレコードを含むホストゾーンです。

**`region`**――前の項目を参照。両方を一緒に設定します。

**`endpoint`**――Endpoint は AWS ではない S3 互換サービスを指します。例えば `http://minio:9000`。空は AWS を意味します。自前のオブジェクトストレージなら、複数のインスタンスが共有ファイルシステムも、どこかのアカウントもなしにひとつのバッファを共有できます。

**`pathStyle`**――PathStyle はバケットを `endpoint/bucket` として指します。endpoint が設定されていれば暗黙に真で、明示のために書く価値があるだけです。

**`accessKeyId`**――AccessKeyID と SecretAccessKey は他のシークレットとともにここに保持される AWS 資格情報で、ひとつのファイルが完全に動くサーバーになるためです。両方を空にすると既定の AWS 資格情報チェーンに切り替わります。環境変数、共有資格情報ファイル、インスタンスロール。EC2 ではインスタンスロールがより良い答えです。漏れる長期の鍵がないからです。

**`secretAccessKey`**――前の項目を参照。両方を一緒に設定します。

**`credentialsFile`**――CredentialsFile は AWS の共有資格情報ファイルで、上の二つの項目の代わりです。

**`nameservers`**――チャレンジのレコードが伝播したか確かめるときに問い合わせるネームサーバー。例えば "ns-1.example.net:53"。

### `database`

他の設定とは一緒に保存されません。データベースに届く方法をデータベースに置くことはできないからです。上で説明した `TEANODE_DATABASE_URL` とその隣の変数から来ます。ここに項目を載せるのは、それらの変数が設定するものだからであり、`config show` が印字するからです。

**`host`**――前の項目を参照。両方を一緒に設定します。

**`port`**――前の項目を参照。両方を一緒に設定します。

**`user`**――前の項目を参照。両方を一緒に設定します。

**`password`**――前の項目を参照。両方を一緒に設定します。

**`name`**――前の項目を参照。両方を一緒に設定します。

**`sslMode`**――SSLMode は PostgreSQL ドライバーに渡されます。disable、allow、prefer、require、verify-ca、verify-full。`require` は接続を暗号化しますが、ポートで答えるものを何でも信じます。`verify-full` はさらに、証明書が `sslRootCertificate` によって署名され、接続先のホスト名が書かれていることを確かめます。これが、ネットワーク上の別の何かがデータベースを名乗って答えるのを防ぐものです。

**`sslRootCertificate`**――SSLRootCertificate は、二つの verify モードでサーバーの証明書を照合する PEM ファイルです。compose ファイルはひとつを生成して `/certs/server.crt` にマウントします。マネージドの PostgreSQL は自身のものを公開しています。空はシステムの信頼ストアを意味し、自己署名証明書はそこにありません。

**`logQueries`**――LogQueries はすべての SQL 文をログに出します。とても騒がしいです。

### `smtp`

**`trustedSenders`**――TrustedSenders は、そのメールが未知の送信者へのグレイリスト遅延を免れるドメインです。

**`maxMessageSize`**――MaxMessageSize は受け付ける最大のメールで、例えば "70MB"。

**`maxRecipientsIncoming`**――MaxRecipientsIncoming は受信メールごとの宛先数を制限します。低い値はアドレス収集をくじきます。

**`maxRecipientsOutgoing`**――MaxRecipientsOutgoing は中継メールごとの宛先数を制限します。

**`greylistDelay`**――GreylistDelay は未知の送信者がメールを受け付けられるまで待たされる時間です。ゼロは遅延なし。

**`requireReverseDns`**――RequireReverseDNS は、自身に解決し返す逆引き DNS レコードのないアドレスからの受信メールを拒否します。既定はオン。安価で、スパムの大半は逆引きレコードのないホストから来るからです。このサーバーが本当のクライアントアドレスを見られないときはオフにしてください。ロードバランサーの後ろ、プライベートネットワーク、テスト中のコンテナネットワーク。そこではこの検査がすべてを拒否します。

**`socks5Proxy`**――SOCKS5Proxy を設定すると、送信 SMTP をプロキシ経由にします。ホスト自身の IP アドレスの評判が悪いときや、送信ポート 25 が塞がれているときに便利です。

**`disableSend`**――DisableSend はサーバーが実際にメールを配送するのを止めます。配送は記録され、未配送のままです。開発マシンで使います。

**`authRateLimit`**――AuthRateLimit はひとつのアドレスがサブミッションポートで毎分何回認証を試せるかで、AuthRateBurst はそのレートが効く前に一度に何回試せるかです。資格情報の検証は HMAC 一回と比較一回で速いので、制限がなければひとつのアドレスがネットワークの許す速さで推測できます。既定はメールクライアントが打ち間違えたパスワードを何度か再試行するのを許し、プログラムがリストをなめるのを止めます。どちらかがゼロなら制限は無効です。

**`authRateBurst`**――`authRateLimit` が効き始める前に、ひとつのアドレスが一度に試せる回数。打ち間違えたパスワードを再試行するメールクライアントは決して当たらないはずで、リストをなめるプログラムは最初の一秒で当たるはずです。

### `smtp.submission`

メールクライアントに接続先として伝えるべきもの。ダッシュボードが新しい資格情報の隣に表示するものです。

通常はサーバーに従います。`server.name` と、`listen.smtpOutgoing` のポート。どちらも空でかまいません。何かが別のポートを転送しているときに設定します。10587 を公開するコンテナや、外で 587 を引き受けるファイアウォール。それなしでは、ダッシュボードはプロセスがたまたまバインドしたポートを人に渡し、それは彼らの携帯電話が届くポートではありません。

サーバーがすることは変わりません。言うことだけが変わります。

**`host`**――接続先。空は `server.name`。

**`port`**――接続するポート。空は `listen.smtpOutgoing` のポート。

### `smtp.relay`

宛先の MX を引いてポート 25 で接続して配送する代わりに、送信メールをひとつのメールサーバーに渡します。

多くの人がこれを必要とするのは、ネットワークが送信ポート 25 を塞いでいるからです。ほぼすべての家庭用 ISP と多くのホスティング事業者がそうしています。侵害されたマシンがスパムを送る手段だからです。リレーはサブミッションポートで届きます。

これはまた、このサーバーがプロバイダー経由で送る方法でもあります。Amazon SES、Postmark、Resend はどれも SMTP エンドポイントを提供するので、プロバイダー固有の設定はなく、メールはこのサーバーがすでに付けた DKIM 署名とともに届きます。彼らの HTTP API は別の話です。組み立て済みのメッセージをそのまま受け付けるのは SES だけで、Postmark と Resend は分解された項目を受け取ります。つまり彼らが署名し直し、あなたの署名は残せません。SMTP エンドポイントを使ってください。

| プロバイダー | ホスト | ポート | セキュリティ |
| --- | --- | --- | --- |
| Gmail | `smtp.gmail.com` | 587 | `starttls` |
| Amazon SES | `email-smtp.<region>.amazonaws.com` | 587 または 2587 | `starttls` |
| | | 465 または 2465 | `tls` |
| Postmark | `smtp.postmarkapp.com` | 587、2525、または 25 | `starttls` |
| Resend | `smtp.resend.com` | 587 または 2587 | `starttls` |
| | | 465 または 2465 | `tls` |

SES はアクセスキーそのものではなく、IAM ユーザーから導いた SMTP 資格情報を必要とし、リージョンごとです。Resend のユーザー名は文字通り `resend` で、パスワードは API キーです。Postmark は両方にサーバートークンを使います。

SES について知っておくべきことがひとつ。`Message-ID` と `Date` を上書きするので、それらのヘッダーを覆う署名は壊れます。このサーバーはそれらに署名しません。

`mailServer` 種別のエイリアスで転送されるメールは影響を受けません。自身の宛先を指定するのがその意味だからです。

**`enabled`**――送信メールがリレーを通るかどうか。

**`host`**――メールを渡すメールサーバー。

**`port`**――通常は 587、465、または 2525。

**`security`**――TLS の使い方。587 と 2525 は `starttls`、465 は `tls`、または `none`。

見知らぬ相手の MX への配送とは違い、どちらの暗号化モードもホスト名に対して証明書を確かめます。ここには照合する名前があり、パスワードが送られようとしているので、どんな証明書でも受け入れることは、答える誰にでもパスワードを渡すことです。`none` は強制しません。STARTTLS が提供されればやはり使います。ただしパスワードが設定されていれば、まっすぐ拒否されます。

**`username`** と **`password`**――何として認証するか。アドレスで認可するリレーでは両方を空にします。

### `dkim`

**`selector`**――新しく作るドメインの鍵に与えるセレクター。DNS には `<selector>._domainkey.<domain>` として現れるので、ドメイン内で一意であればよく、ここで変えても既存のドメインには影響しません。

### `domains[]`

**`id`**――ID は保存されたメール、配送記録、使用量の行、そしてダッシュボードの URL でドメインを識別します。それはドメインそのものです。すでに一意で、ドメインが設定されている間は安定し、現れる場所ではどこでも読めます。生成された識別子をここに持つ古い設定もそのまま動きます。それを参照する行は一致し続けます。変えることはそれらの行も更新することを意味するので、何も自動で書き換えません。

**`domain`**――Domain はメールドメインそのもので、例えば "example.com"。

**`subdomain`**――Subdomain は、バウンスと DMARC レポートが届く場所を持つよう、CNAME でこのサーバーを指すラベルです。通常は "mail" で、mail.example.com を server.name への CNAME にします。

**`linkHost`**――LinkHost は、このサーバーが送るメールに書き込むアドレスの中の名前です。今のところテンプレートの画像で、それぞれがひとつのメッセージに属するアドレスです。空はドメインの最初のメールサーバー名を意味し、このサーバーがその名前で HTTPS に答えるなら正しいです。そうでないことはよくあります。メールサーバー名の解決先ホストのポート 443 はまったく別のものに属し、するとすべてのメールのすべての画像が壊れ、メールそのものは正常です。ここの名前は、このドメインの HTTPS が実際どこにあるかを言う方法です。CDN の後ろの頂点サイト、そのためにこのサーバーを指す名前。メールが届く場所を動かすことなく。HTTPS で、メールリーダーが受け入れる証明書とともにこのサーバーに届く名前でなければならず、このドメインの下でなければなりません。他人のドメインの下のアドレスは読者に誰がサーバーを動かしているかを教え、それはドメインごとの名前が防ぐためにあることです。

**`comment`**――Comment は運用者へのメモで、メール処理は決して使いません。

**`dkim`**――DKIM はこのドメインから送るメールに署名する鍵です。ドメイン作成時に生成され、対応する公開鍵は DNS に公開しなければなりません。ダッシュボードが見せてくれます。

**`spamFilterScoreThreshold`**――SpamFilterScoreThreshold は、それ以上でメールが拒否される SpamAssassin のスコアです。antispam が有効なときだけ意味があります。

**`aliases`**――Aliases はこのドメインのメールがどこへ行くかを決めます。パターンが一致するすべてのエイリアスが配送を生むので、ひとつのアドレスを複数の場所へ転送できます。パターンが空のエイリアスはキャッチオールで、他のどれにも一致しなかったメールだけを受け取ります。

**`credentials`**――Credentials はサブミッションポートで認証し、このドメインとして送れます。

### `domains[].dkim`

**`selector`**――この鍵が公開されるセレクター。

**`privateKey`**――PrivateKey は PEM の PKCS#8 RSA 鍵です。

### `domains[].aliases[]`

**`id`**――ID は一度生成されて決して変わりません。保存された配送記録がそれを参照します。

**`pattern`**――Pattern は Go の正規表現で、宛先アドレスのローカル部（"@" の前）に大文字小文字を区別せず一致します。アンカーを付けてください。"^hello$" は hello@ だけに一致し、"hello" は say-hello-now@ にも一致します。メールボックスへ配送するエイリアスは、ウェブ UI や API から作るときに自動でアンカーが付きます。「hello」が「^hello$」になるのは、メールボックスのアドレスがそのパターンから読み戻されるからです。`config import` で読み込んだファイルは書かれたとおりに扱われます。空のパターンはキャッチオールにします。キャッチオールは予備です。どのパターンにも一致しないアドレスのメールだけを受け取るので、加えてもすでに行き先のあるメールが重複することはありません。

**`comment`**――Comment は運用者へのメモです。

**`kind`**――Kind は null、email、webhook、mailServer のいずれかです。

**`email`**――Email は kind が email のときの宛先アドレスです。

**`webhook`**――Webhook は kind が webhook のときの宛先 URL です。

**`mailServer`**――MailServer は kind が mailServer のときの宛先サーバーです。

**`disabled`**――Disabled はエイリアスを削除せずに一致を止めます。

### `domains[].credentials[]`

**`id`**――ID は保存されたメール、配送記録、使用量の行、そしてダッシュボードの URL でドメインを識別します。それはドメインそのものです。すでに一意で、ドメインが設定されている間は安定し、現れる場所ではどこでも読めます。生成された識別子をここに持つ古い設定もそのまま動きます。それを参照する行は一致し続けます。変えることはそれらの行も更新することを意味するので、何も自動で書き換えません。

**`alias`**――Alias を設定すると、この資格情報をドメインのこのローカル部としてだけ送れるよう制限します。"noreply" の資格情報は他の誰としても送れず、漏れたときの被害を限定します。

**`email`**――Email は通知を受け取ります。例えばドメインの DNS レコードが解決しなくなったとき。任意です。

### `antispam`

迷惑メールの採点。メールが比べられるスコアはドメインの `spamFilterScoreThreshold` であって、ここの設定ではありません。

**`enabled`**――そもそもメールを採点するかどうか。

**`engine`**――採点するのは何か。`builtin` はこのサーバー内蔵のフィルター、`spamd` は外部の SpamAssassin デーモンです。空のままは既定値ではなく解決されます。すでにデーモンと話している配備が、手を入れずにそのまま動き続けるためです。空でホストが設定されていれば `spamd`、空でホストがなければ `builtin` です。

**`spamd`**――外部デーモンがどこで待ち受けているか。`engine` が `spamd` のときに使います。項目は `host` と `port` の二つです。

**`host`**、**`port`**――非推奨。`spamd` を使ってください。現場の配備が保存しているのがこれで、いまも動くので残されています。

**`builtin`**――このサーバー内蔵のフィルター。サーバーがすでに知っていること、公開ブロックリスト、自分のメールで訓練した分類器、そして任意で公開のパターンルールから採点します。以下の四つのグループは独立にオンオフできます。

**`signals`**――サーバーがそのメールについてすでに確定させたことからの採点。認証の結果、送信ホストの確認済み逆引き名、HELO で名乗った名前です。採点が始まる前にすべて計算済みなので、問い合わせの費用はかかりません。項目は `enabled` ひとつです。

**`dns`**――公開ブロックリストでの評判の照会。ブロックリストは普通の DNS 問い合わせで引くので、これ自体のためのサービスは要りません。

**`timeout`**――一通のメールに対するブロックリスト照会全体を制限します。

**`addressLists`**――接続元アドレスについて問い合わせるリスト。各項目に `zone` と `weight` があります。

**`domainLists`**――メールの中に見つかったドメインについて問い合わせるリスト。各項目に `zone` と `weight` があります。

**`zone`**――問い合わせを組み立てる接尾辞。たとえば `zen.spamhaus.org`。

**`weight`**――載っていた場合に加える点数。

**`maximumDomains`**――一通のメールから引くドメインの数に上限をかけます。リンクだらけのメールが DNS 問い合わせの束にならないように。

**`bayes`**――このサーバー自身のメールで訓練した分類器。ダッシュボードで迷惑メールか否かの印を付けたメールが教材です。実際に届くメールを学ぶので、迷惑メールフィルターの中でたいてい最も正確な部分です。

**`minimumMessages`**――分類器が何かを寄与してよくなるまでに、いくつのメールを学んでいる必要があるか。四通で訓練した分類器は、自信を持って間違えます。

**`rules`**――公開のパターンルール。データベースに取り込み、このプロセスで評価します。既定ではオフ。アップグレードが、誰も頼んでいないルールファイルの取得と実行を勝手に始めるべきではないからです。

**`channels`**――取得する更新チャンネルを名前で。

**`updateInterval`**――ルールの新しい版をどれくらいの頻度で探すか。

**`maximumEvaluationTime`**――一通のメールのルール評価全体を制限します。攻撃者が選んだ文章の上を何千ものパターンが走るので、これは目標ではなく上限です。

ルールは無人でダウンロードされるのではなく、意図して読み込まれます。

    teanode-server config rules import --file ruleset.cf --channel updates.spamassassin.org
    teanode-server config rules show

ルールはディレクトリではなくデータベースに保存されます。ひとつのサーバーが複数のインスタンスとして動くことがあり、それらは同じルールを評価しなければならないからです。各インスタンスは新しい版に一分以内に気づきます。`show` は、いくつのルールが読み込まれ、いくつが飛ばされたかを報告します。公開されたルール集には、このサーバーが持たないプラグインで実装されたルールや、正規表現エンジンがコンパイルできないパターンが含まれており、どちらも推測せずに外されます。

自動ダウンロードはありません。ルールは受け取るすべてのメールに対してこのサーバーが走らせるパターンなので、無人で取得するということは発行者の署名を検証するということであり、それを行う OpenPGP パッケージは上流で非推奨になっています。凍結した暗号ライブラリへの依存をメールサーバーに加えるのは、意図して下すに値する決定です。

`updates.spamassassin.org` で公開されているルールデータは Apache SpamAssassin プロジェクトが作り、Apache License 2.0 で提供されています。内蔵のフィルターは別のプログラムであり、SpamAssassin ではありません。あなたが有効にして読み込んだときにだけ、その公開されたルールデータを読みます。

### `geoip`

**`enabled`**――前の項目を参照。両方を一緒に設定します。

**`databaseFile`**――DatabaseFile は MaxMind の .mmdb ファイルです。

### `storage`

**`directory`**――Directory は生のメールを、server.dataDirectory を基準に保持します。データベースには置きません。大きく、問い合わせられることがなく、バックアップを高価にするからです。

**`spoolRetention`**――SpoolRetention はメールが保持される長さで、ダッシュボードがどこまで遡って内容を見せられるか、そして止まった配送がどれだけ長く再試行できるかです。ゼロは永久に保持し、いずれディスクを埋めます。

**`s3`**――前の項目を参照。両方を一緒に設定します。

### `storage.s3`

**`enabled`**――前の項目を参照。両方を一緒に設定します。

**`bucket`**――前の項目を参照。両方を一緒に設定します。

**`region`**――前の項目を参照。両方を一緒に設定します。

**`endpoint`**――Endpoint は AWS ではない S3 互換サービスを指します。例えば `http://minio:9000`。空は AWS を意味します。自前のオブジェクトストレージなら、複数のインスタンスが共有ファイルシステムも、どこかのアカウントもなしにひとつのバッファを共有できます。

**`pathStyle`**――PathStyle はバケットを `endpoint/bucket` として指します。endpoint が設定されていれば暗黙に真で、明示のために書く価値があるだけです。

**`accessKeyId`**――AccessKeyID と SecretAccessKey は他のシークレットとともにここに保持される AWS 資格情報で、ひとつのファイルが完全に動くサーバーになるためです。両方を空にすると既定の AWS 資格情報チェーンに切り替わります。環境変数、共有資格情報ファイル、インスタンスロール。EC2 ではインスタンスロールがより良い答えです。漏れる長期の鍵がないからです。

**`secretAccessKey`**――前の項目を参照。両方を一緒に設定します。

**`credentialsFile`**――CredentialsFile は AWS の共有資格情報ファイルで、上の二つの項目の代わりです。

### `passkey`

**`enabled`**――Enabled はサインインフォームとアカウント設定でパスキーを提供します。既定はオフ。平文の HTTP で届くサーバーや、名前がこれから変わるサーバーでパスキーを登録すると、後で使えないものが生まれるからです。

**`relyingPartyId`**――RelyingPartyID は資格情報が結び付くドメインで、スキームとポートなし。`mail.example.com`、または同じパスキーをすべてのサブドメインで使えるようにする `example.com`。空は `server.name`。WebAuthn は資格情報を永久に結び付けるので、間違った名前で登録したパスキーは二度と使えず、修復もできず、削除するしかありません。

**`displayName`**――DisplayName は、ブラウザーが誰かにパスキーの作成や使用を求めるときに表示する名前です。空は `server.name`。

**`origins`**――Origins はダッシュボードのオリジンで、それぞれスキームと既定でないポート付き。`https://mail.example.com`。載っていないオリジンからのアサーションは拒否され、これが別のサイトのページがこれらの資格情報を使うのを止めるものです。空は `https://` にリライングパーティを付けたもの。

**`maximumPerUser`**――MaximumPerUser はひとつのアカウントが登録できる数を制限します。ゼロは五つ。携帯電話、ノート PC、セキュリティキー、そして削除する前に置き換える余裕です。

### `passkey.redis`

進行中のパスキーサインインが待つ場所。WebAuthn のサインインは二つのリクエストで、ロードバランサーの後ろではブラウザーが最初のインスタンスに戻る理由がないので、最初のリクエストが作ったチャレンジは二つ目が見つけられる場所に置く必要があります。インスタンスがひとつなら address を空にし、チャレンジはプロセス内に留まります。どちらにせよ永続的なものはここに置かれず、すべて失っても再試行一回分の損失です。

**`address`**――Address、host:port の形式。例えば `redis:6379`。空は無効。

**`username`**――Username、サーバーが要求するとき。

**`password`**――Password、サーバーが要求するとき。

**`database`**――Database 番号。他の何かがサーバーを共有しているのでなければゼロ。

### `upgrade`

**`enabled`**――Enabled は CheckInterval ごとにリリース一覧に最新バージョンを尋ね、ダッシュボードに表示します。公開エンドポイントへの HTTPS リクエスト一回で、このデプロイについての情報は何も持ちません。既定はオン。バージョンの存在を知ることはそれをインストールすることではなく、決して知らされない運用者は去年のバグを動かしている運用者だからです。

**`automatic`**――Automatic は見つけたものを尋ねずにインストールします。ダウンロードし、リリースのチェックサムで検証し、このバイナリを置き換え、再起動します。既定はオフ。リリースはメールの扱いを変えるかもしれず、足元で静かに変わるメールサーバーを望んでインストールする人はいないからです。マイナーもメジャーも、新しいバージョンなら何でも受け入れます。マイナーで止まる規則は、静かに更新をやめる規則です。

新しいバイナリを置く場所がないと拒否され、理由がダッシュボードに表示されます。自身の実行ファイルを上書きできず、`TEANODE_UPGRADE_DIRECTORY` で書き込めるステージング場所を与えられていないデプロイです。コンテナは拒否されません。自身のデータボリュームにステージし、次の起動でそれを実行するので、更新はコンテナの再作成を生き延びます。ただしそのようなボリュームを与えられなかったコンテナは拒否され、そのときは `docker compose pull` が答えです。

再起動に監督者は要りません。プロセスはすべてを排出して閉じた後、同じ引数と環境で自身のイメージを新しいバイナリに置き換えます。ですから手で始めたサーバーも systemd の下のものと同じように自分を更新します。

**ひとつ制限があり、自動更新を最も気軽にオンにしそうな種類のデプロイに最も強く当たります。** 起動を終える前にクラッシュするリリースが自動で復旧されるのは、新しいバイナリが古いものを上書きするのではなくステージされる場所だけです。コンテナはイメージ内のバイナリを再び実行し、理由を告げます。バイナリがその場で置き換えられる場所では、自力で戻るものが何もありません。監督者は誰かが止めるまで壊れたバイナリを再起動し続けます。置き換えられたバイナリはその隣に残るので、復旧はコマンドひとつ、

    mv /usr/local/bin/teanode.previous /usr/local/bin/teanode

そして再起動です。自動更新はステージするデプロイでより価値があり、しないデプロイでは二度考える価値があります。

**`checkInterval`**――CheckInterval はどれくらいの頻度で見に行くかです。既定は六時間。セキュリティリリースが当日に気づかれるには十分頻繁で、誰かが気づくほどのリクエストにはならないほど稀です。起動時に一度読まれるので、変えるには再起動が要り、ダッシュボードがそう言います。`enabled`、`automatic`、`window` はループが目覚めるたびに読み直され、再起動なしに効きます。

ループ自体はこれより頻繁に目覚め、ほとんどの時は何も尋ねません。それが `window` を動かすものです。六時間ごとの確認は一日の四つの固定した瞬間に起き、二時間の窓はプロセスがいつ始まったかによって当たったり外れたりします。

**`window`**――Window は自動更新を一日のうちの時間帯に、現地時間で `02:00-04:00` のように限ります。真夜中をまたげます。空はいつでも。更新はサーバーを再起動し、その間数秒メールを受け取りません。送信者は再試行しますが、忙しい時間帯はやはり静かな時間帯より悪いです。

ここでの検証が何を意味するか、はっきりさせておきます。バイナリとリリースの `SHA256SUMS` は、このサーバーがビルドされたリポジトリから HTTPS で取得され、ハッシュは一致しなければなりません。これは、これらのバイトが GitHub がそのバージョンのために提供したバイトであり、ダウンロードが壊れていないことを証明します。誰かが意図してそれを公開したことは証明しません。そのリポジトリにリリースを公開できる誰もがバイナリを公開でき、これはそれをインストールします。リポジトリは設定ではなくコンパイル時に埋め込まれるので、盗まれたダッシュボードのセッションがサーバーを他人のビルドに向けることはできません。

### `users[].tokens[]`

**`id`**――ID はトークンを識別し、トークン文字列の秘密でない半分です。ログに現れるので、トークンはここの項目まで辿って失効させられます。

**`name`**――Name は何がそれを持つかを言います。例えば "laptop"。一意ではありません。

**`hash`**――Hash は秘密の半分の SHA-256 で、十六進エンコードです。トークンは 32 のランダムなバイトなので、遅いハッシュで守るものは何もありません。パスワードと違って推測できないからです。

**`created`**――Created は発行された時刻を、運用者の便宜のために記録します。

**`expires`**――Expires を設定すると、動かなくなる時刻です。
