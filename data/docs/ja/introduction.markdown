TeaNode は、サイドプロジェクトにも、立ち上げたばかりのスタートアップにも、それぞれのドメインで本物のメールアドレスを与えます。そのたびにメールボックスを運用する必要はありません。

小さなセルフホストのメールサーバーです。すべてのドメイン宛のメールを SMTP で受け取り、本物かどうかを確かめ（SPF、DKIM、DMARC、ARC）、必要ならウイルスとスパムをスキャンして、指定した先へ転送します。本当に使っているメールボックスへ、webhook へ、あるいは別のメールサーバーへ。自分のデバイスからの送信メールも中継し、ドメインの鍵で署名するので、迷惑メール扱いにならず相手に届きます。

メールボックスサーバー**ではない**ことは、意図したものです。IMAP も受信箱もありません。メールは今読んでいる場所でそのまま読み続けてください。TeaNode が受け持つのは、ドメインと、認証と、ルーティングです。

## なぜ

ドメインのメールを運用するには、たいていプロバイダーに預けるか、Postfix、Dovecot、OpenDKIM、OpenDMARC、SpamAssassin とポリシーデーモンを組み合わせて、それらの足並みを揃え続けるかのどちらかです。これは実行ファイルひとつと PostgreSQL データベースひとつで、メールを信頼できるかどうかを決める認証は、後付けではなく組み込みです。

## 必要なもの

- ドメインと、その DNS を編集できること
- 固定アドレスを持ち、ポート 25、80、443、587 に到達できるホスト
- 設定と扱ったメールを保存する PostgreSQL

他には何もいりません。AWS のアカウントも Redis も不要です。証明書は HTTP-01 で自動取得されるので、設定する DNS API もありません。S3 互換のオブジェクトストアは任意で、複数のインスタンスを動かすときにだけ意味があります。保存したメールをインスタンス同士で共有するためのものです。

## できること

**すべてを認証する。** 受信時に SPF、DKIM、DMARC、ARC を検査し、結果をメールごとに表示します。送信メールには DKIM 署名を付け、転送するメールには ARC チェーンを残すので、転送先でも検証を通ります。

**柔軟に転送する。** エイリアスは正規表現でアドレスを照合し、メールアドレス、HTTP エンドポイント、または別のメールサーバーへ送ります。空のパターンはキャッチオールで、他のどれにも一致しなかったものを受け取ります。

**送信メールを中継する。** サブミッションポートにデバイスごとの SMTP 資格情報を用意し、それぞれを送信元アドレスひとつに制限することもできます。

**メールを見せる。** ダッシュボードはメールをメールとして表示します。認証の判定、配送の試行とその失敗の理由、そしてスクリプトを取り除いた本文。リモート画像は求めるまで読み込みません。

**書いたメールを送る。** 変数と翻訳を持つテンプレート、それを包むレイアウト、自分のドメインから配信する画像、そして受信者のメールソフトがそれを取得したかどうかの記録。

**ドメインについて報告する。** 受け取った DMARC 集計レポートは解析して保存されます。誰かが自分のドメインを偽っていることに気づけるのは、これのおかげです。

**任意の追加機能、すべて既定でオフ。** ClamAV、SpamAssassin、GeoIP、保存メールの S3 ミラー、アドレスの評判が悪いホスト向けの送信 SOCKS5 プロキシ、ワイルドカード証明書が必要なときの DNS-01。

## メールはどう通り抜けるか

1. SMTP リスナーがプロトコルを話し、必要なら STARTTLS と認証を行い、エンベロープを作ります。
2. エンベロープが四つの経路のどれかを選びます。署名付きのバウンス宛先やレポート宛先なら配送状態通知か DMARC 集計レポート、資格情報があれば送信のサブミッション、それ以外は受信メールです。
3. 受信メールは検査されます。SPF、DKIM、DMARC、ARC を並行して行い、続いて任意のウイルスとスパムのスキャン。それぞれの検査が下した判断とともに記録されます。宛先のローカルパートをそのドメインのエイリアスと照合し、一致ごとにひとつの配送を作ります。メールボックス、webhook、または別のメールサーバーへ。
4. 送信メールはドメインの鍵で署名され、中継されます。失敗した配送は固定のバックオフの段階で再試行され、キューのページが失敗の理由を相手のサーバー自身の言葉で示します。

どの段階も、ダッシュボードが何が起きたかを見せられる場所です。記録するのはそのためです。

## 設定

設定はデータベースにあります。だから複数のインスタンスがひとつの答えを共有し、ダッシュボードでの変更はすべてのインスタンスに届きます。環境変数が言うのはデータベースがどこにあるかだけで、それ以外はすべて保存されています。

```yaml
domains:
  - id: example.com
    domain: example.com
    subdomain: mail
    aliases:
      - id: 01K2ZQ7B8N6H4K2QDX8ZR5VTAE
        pattern: ^hello$
        kind: email
        email: you@example.net
      - id: 01K2ZQ7B8PA1M7CJW3YFB9SDQK
        pattern: ""            # キャッチオール
        kind: email
        email: everything@example.net
```

これが `teanode-server config show` の出力であり、`teanode-server config import` が読むものです。サーバー全体をひとつのファイルに書き、バージョン管理に置き、読み込ませることができます。ただし、動いているサーバーの答えはデータベースです。[設定](/doc/configuration)にすべての項目が書かれています。
