TeaNode はメールサーバーです。メールは容赦がありません。間違いは例外を投げず、誰かのメッセージを黙って失うか、ドメインの評判を焼き払います。以下の大半はそこから来ています。

まず [`docs/reference/local-development.md`](/doc/local-development) で、ビルドとデータベースを用意してください。

## 変更を送る前に

    make format        # gofmt
    make lint          # golangci-lint、それから命名チェック（入れていれば）
    make test          # PostgreSQL のコンテナを自動で起動する
    make build

CI は `make lint-ci` を実行します。golangci-lint だけです。このプロジェクトの命名規約を強制するローカルのチェックはローカル専用なので、それを持たない貢献者が止められることはありません。持っているなら実行してください。

## 命名

これらは交渉の余地がなく、`make lint` がほとんどを検査します。

- **頭字語は最初の文字に従う。** 識別子が大文字で始まるなら、頭字語はすべて大文字です。`ReferenceURI`、`SessionID`、`GetFTPID`、`DKIMResult`。小文字で始まるなら、頭字語の最初の文字だけを大文字にします。`referenceUri`、`sessionId`、`getFtpId`。新しい頭字語は、何の略かを書いたコメントとともに lint の設定に登録してください。
- **省略しない。** `cmd` ではなく `command`。`resp` ではなく `response`。`req` ではなく `request`。Go のパッケージ名は例外で、短くあるべきです。
- **一文字の変数は使わない。** `err` だけが認められた短い名前で、Go のエラーは可能な限り `err` と呼びます。
- **構造体のレシーバーは `self`。** コードベース全体で一貫して。`.golangci.yml` はこれに異議を唱えるリンターを無効にしています。
- **同じものはどこでも同じ名前で呼ぶ。** データベースで `delivery` なら、API で `send` ではありません。

## コメント

**なぜ**を説明し、何をしているかは説明しません。何をしているかは下のコードにあります。

コメントが価値を持つのは、読者がコードから復元できないことを記録しているときです。プロトコルの要件、本番で観察された故障、いくつかの妥当な選択肢からの意図的な選択。`counter++` の上の `// increment the counter` は雑音です。`// Reject before the DATA command so a spammer pays for the connection` は書く価値があります。

エクスポートされる識別子には、その名前で始まるドキュメントコメントを付けます。

## 不変条件

どれかを破ると、下流の何かが追跡しにくい形で壊れます。

- **すべてのマイグレーションは対になる `.reverse.sql` を伴う。** `internal/db/database_migrate.go` のマイグレーションランナーは、適用時に記録した逆向きの SQL で未知のマイグレーションを取り消し、それがなければ panic します。[`docs/coding/database-migrations.md`](https://github.com/ziyan/teanode/blob/main/docs/coding/database-migrations.md) を参照してください。
- **設定の識別子は安定している。** 設定中のドメイン、エイリアス、資格情報の `id` は一度生成されたら変わりません。保存されたメールと配送がそれを参照しているからです。パターンを編集しても id を再生成してはいけません。
- **保存された設定が唯一の真実。** それはひとつの文書としてデータベースにあり、`internal/config` がその形を定めます。自前の設定テーブルを追加せず、使う場所で環境変数を読まないでください。環境変数はデータベースの場所を告げ、初回起動の種になるだけで、運用者が設定するそれ以外のすべては `internal/config` に属します。
- **既定のコードパスにクラウド依存を置かない。** S3、Route53、GeoIP は任意で、既定ではオフです。`if settings.Enabled` で守られたコードは、無効のときにクライアントを構築したり、ファイルを開いたり、どこかに接続したりしてはいけません。
- **ACME `http-01` のハンドラーが最初に来る。** 認証局は `/.well-known/acme-challenge/` を平文の HTTP で、資格情報なしに取得します。認証、HTTPS へのリダイレクト、キャッチオールのルートに出会ってはいけません。
- **サーバーシークレットは一度だけ生成される。** バウンスの返送経路と、すべての SMTP 資格情報のパスワードに署名します。ローテーションするとそのすべてが無効になります。
- **シークレットや実在のアドレスをコミットしない。** `make check-secrets` が追跡されているファイルを走査します。テストのフィクスチャは `example.com` と `example.net` を使います。

## テスト

そのバグを捕まえられたはずのテストを書いてください。コードが動くことしか証明しないテストは、維持する価値がありません。

PostgreSQL を必要とするテストは `internal/db/dbtest` からそれを受け取り、`TEANODE_TEST_DATABASE_HOST` が未設定ならスキップするので、Docker がなくても `go test` は動きます。

**ユニットテストはネットワークに触れてはいけない。** これは痛い目を見て学んだことです。初期の `autoacme.Open` は構築時に更新ループを開始したので、テストでマネージャーを作っただけで Let's Encrypt の本番環境に接続しました。まさにそのため、構築と開始はいま分かれています。

## コミット

一年後に、それを生んだ会話の記憶なしにこの変更を理解しようとする人のためにメッセージを書いてください。

- 件名は命令形で、およそ 72 文字以内。"Obtain certificates without a cloud account"。
- 本文は、なぜ変更が必要だったか、何を犠牲にするかを説明します。diff が何をしているかの説明は冗長です。diff はそこにあります。
- 運用者にとって変わった振る舞いと、アップグレード時に手でやらなければならないことを記します。

## 変更履歴

利用者に見える変更には変更履歴の項目が必要で、書く場所は二つあります。ほとんどはプルリクエストの説明の Changelog ブロックに書きます。説明する変更と一緒にレビューされ、リリースボットが集めます。`CHANGELOG.md` の Unreleased の下に直接書くのがもうひとつの方法で、main に直接コミットする人がそうします。運用者に観察できない内部のリファクタリングにはどちらも不要です。説明でそう言い、プルリクエストに `no changelog` のラベルを付けてください。

その項目が変更をリリースするものでもあります。Unreleased の下に何かを残す `main` へのプッシュはすべてリリースに切られます。バージョンは項目から決まり、`Added` か `Removed` なら新しいマイナー、それ以外なら新しいパッチで、プッシュされるタグがバイナリとコンテナイメージをビルドします。Unreleased の下に何もないプッシュは何もリリースしません。ほとんどのプッシュがそうです。

プッシュする前に何が起きるかを見るには、

    .github/scripts/cut-release.sh          # バージョンを告げる。何も書かない
    .github/scripts/changelog.sh 0.2.0      # そのバージョンが持つ説明

ノート PC では `CHANGELOG.md` しか読みません。そう告げ、理由も告げます。プルリクエストを読むには `GITHUB_REPOSITORY` とトークンが必要で、ワークフローがそれを渡します。

メジャーバージョンは決して推測されません。ある変更がこれを動かしている人を壊すと決めるのは判断なので、手で実行する "Major release" ワークフローで、MAJOR という語を入力します。

## 決定

変更が、将来の読者が疑問に思うような選択をするなら、`docs/decisions/` に決定記録を書いてください。そこにある README を参照してください。大きな作業はまず `docs/planning/active/` に設計文書を書き、着地したら `done/` へ移します。

## セキュリティ問題の報告

メールの処理、認証、証明書の発行で悪用できる問題については、公開の issue を立てないでください。[`SECURITY.md`](/doc/security) が行き先を示しています。Security タブからの、GitHub のプライベートな脆弱性報告です。
