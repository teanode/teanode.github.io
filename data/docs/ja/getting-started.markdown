ひとつのドメインのメールサーバーを、何もない状態からメールが届いて転送されるまで立ち上げます。二十分ほどかかり、その大半は DNS を待つ時間です。

## 始める前に

必要なものは三つです。

- **ドメイン**と、その DNS レコードを編集できること。
- **固定アドレスを持つホスト**。インターネットからポート 25、80、443、587 に到達できること。
- **PostgreSQL**。すべてを保持します。設定、署名鍵、そしてサーバーが扱ったメール。バックアップすべき唯一のものです。

### ポート 25 の問題

ホストを借りる前にここを読んでください。ほとんどの家庭向け ISP と、少なからぬクラウド事業者は、**送信**のポート 25 を既定で塞いでいます。DigitalOcean、Google Cloud、Azure、Oracle Cloud はすべてそうで、Amazon EC2 も申請するまではそうです。

受信のポート 25 はたいてい問題ありません。塞がれるのは送信で、それがないとこのサーバーはメールを受け取れても配送できません。転送は失敗し、それでいてすべてが健全に見えます。

決める前に確かめてください。

    nc -vz gmail-smtp-in.l.google.com 25

これが止まるか拒否されるなら、選択肢は三つです。事業者に解除を頼む、塞いでいない事業者を選ぶ、あるいは `smtp.socks5Proxy` を設定して、ポート 25 に届くホスト経由で送信メールを流す。

## 1. インストール

    curl -L -o /usr/local/bin/teanode-server \
      https://github.com/ziyan/teanode/releases/latest/download/teanode-server-linux-amd64
    curl -L -o /usr/local/bin/teanode \
      https://github.com/ziyan/teanode/releases/latest/download/teanode-linux-amd64
    chmod +x /usr/local/bin/teanode-server /usr/local/bin/teanode

`teanode-server` がサーバーで、ダッシュボードはその中にあります。他にインストールしたり配信したりするものはありません。`teanode` はサーバーを管理するクライアントで、サーバー上にも自分のマシンにも置くものです。macOS 向けのビルドがあります。

両方のバイナリが入ったコンテナイメージもあり、それがこれを動かすより良い方法です。**[reference/deployment.md](https://github.com/ziyan/teanode/blob/main/docs/reference/deployment.md)** を参照してください。ここの手順 1 と 2 の代わりになります。このページの残り、DNS とダッシュボードの取得は、どちらの方法でも当てはまります。

## 2. サーバーを記述する

設定は PostgreSQL にあります。環境変数はそこへ辿り着く方法と、空のデータベースに対してサーバーが初めて起動するときに、どんなサーバーを作るかを伝えます。

    mkdir -p /opt/teanode && cd /opt/teanode
    teanode-server config env --output .env \
      --hostname mail.example.com \
      --domain example.com

`--hostname` はこのサーバーの名前です。サーバーが SMTP で名乗る名前であり、MX レコードが指す名前なので、DNS レコードを追加できる名前でなければなりません。

`--domain` はメールを受け取りたいドメインです。このサーバーが扱う最初のドメインになります。

`.env` を開いて、`TEANODE_DATABASE_URL` に PostgreSQL を、`TEANODE_TLS_ACME_EMAIL` に認証局が期限切れを知らせられるアドレスを設定します。それからデータベースを用意します。

    set -a; . ./.env; set +a
    teanode-server config init

これがマイグレーションを実行し、設定を保存します。ドメインの DKIM 署名鍵とサーバーシークレットが生成され、以後はどちらもデータベースにあります。だからバックアップすべきものはデータベースです。

これ以降 `.env` はデータベースの場所を読むためだけに使われます。設定はダッシュボードで変えるもので、保存された値と食い違う初回起動用の変数があれば、サーバーはログでそう言います。

### 既存のサーバーを移す

この配備がすでに `teanode.yaml` で動いていたなら、新しく作るのではなくそれを読み込みます。識別子、署名鍵、サーバーシークレット、セッション鍵はそのまま引き継がれるので、保存されたメールは引き続き解決でき、SMTP のパスワードは有効なまま、誰もサインアウトされません。

    teanode-server config import --file /opt/teanode/teanode.yaml

## 3. DNS を公開する

何を公開すべきかサーバーに尋ねます。

    teanode dkim show example.com

必要なレコードは四つです。最初のひとつだけがメールが届くかどうかを決め、残りは信頼されるかどうかを決めます。

| 種類 | 名前 | 値 |
| --- | --- | --- |
| A | `mail.example.com` | サーバーのアドレス |
| MX | `example.com` | `10 mail.example.com` |
| TXT | `example.com` | `v=spf1 mx -all` |
| TXT | `teanode1._domainkey.example.com` | `dkim show` が出力したもの |

それぞれについて。

- **A** — MX の名前は解決できなければならず、しかも*この*ホストに解決される必要があります。事業者が許すなら、そのアドレスの逆引き DNS も一致させてください。受信側のサーバーは確認します。
- **MX** — これがなければ、他がどれだけ正しくてもメールは届きません。サーバーを指すレコードひとつで十分です。メールを二つの名前、`mx1` と `mx2` で受けたいなら、後でサーバーを移すときにドメインごとに DNS を変えずに済むように、`server.mailServers` に列挙すると、ダッシュボードが各ドメインに両方を求めます。
- **SPF** — `v=spf1 mx -all` は「私の MX レコードにあるホストが私のメールを送り、他は送らない」という意味です。このドメインとして別のものがメールを送るなら、ニュースレターのサービスや CRM など、ここに加えてください。さもないとそのメールは失敗し始めます。
- **DKIM** — 送信メールに署名し、受信側が改ざんされていないこと、本当にあなたからのものであることを確かめられるようにします。

メールが流れ始めたら、五つ目を加えます。

    TXT   _dmarc.example.com   v=DMARC1; p=none; rua=mailto:rua@mail.example.com

`p=none` は誰にも何も拒否するよう求めません。レポートだけを求め、サーバーがそれを解析して見せます。レポートが自分のメールの通過を示すようになったら、`p=quarantine`、そして `p=reject` へ進んでください。

## 4. 確認して起動する

    teanode-server config validate
    teanode-server run

最初の起動でサーバーは HTTP-01 で証明書を取得します。これにはインターネットからポート 80 に到達できることが必要です。できなければ、ログが最初にそれを告げます。

### root で動いていたコンテナのアップグレード

イメージはいま root ではなく uid 65532 で動き、低いポートを bind するための `CAP_NET_BIND_SERVICE` だけを持ちます。データディレクトリが以前のバージョンで作られたなら root の所有で、サーバーは読めません。新しいイメージを起動する前に一度だけ。

    chown -R 65532:65532 /opt/teanode/data/teanode

## 5. ダッシュボードを取得する

`https://mail.example.com/` を開きます。最初の訪問者が唯一のアカウントを作るので、すぐにやってください。サーバーが到達可能になって、誰かに見つけられるほど時間が経つ前に。競争したくなければ、

    teanode user add you

ダッシュボードは、どの DNS レコードがまだ欠けているか、間違っているかをドメインごとに正確に示すので、推測ではなく何が残っているかが分かります。定期的に確認するので、再読み込みは不要です。

### 締め出されたら

メールでのパスワードリセットはありません。戻る道はサーバー自身のホストです。そこで、サーバーの環境変数をシェルに入れれば（コンテナにはすでにあります）、クライアントはコンソールとしてサーバーに届き、アカウントの追加やパスワードの設定ができます。

    teanode user create you
    teanode user password you

    docker compose exec teanode teanode user create you      # コンテナの中で

サーバーが動いていないとき、あるいは動いていても誰もサインインできずコンソールも届かないときは、`teanode-server user` が保存された設定を直接編集します。必要なのはデータベースだけです。

    teanode-server user list
    teanode-server user add you
    teanode-server user password you

`teanode-server user reset` はすべてのアカウントを消し、その後ダッシュボードを次に開いた人が初日と同じようにアカウントを作ります。誰かが取得するまでは、ダッシュボードに届く人なら誰でも取得できるので、その状態のまま放置しないでください。

こうして作られたアカウントは管理者で、Personal という自分のメールボックスを持ちます。ウェブ UI はそこから始まります。左の欄にフォルダー、その隣にフォルダーのメール、さらに隣に読んでいる一通。管理のページ——サーバーが扱ったすべてのメール、キュー、レポート、ドメイン、サーバー自身——は左欄の下の **管理** の向こうにあり、上の **メールボックスに戻る** で戻ります。

受信箱と **スター付き**（どこにあっても印を付けたすべてのメール）は左欄の上に留まります。他のフォルダーにカーソルを合わせると出るピンで、それも上に並べられます。検索ボックスは開いているフォルダーの中を、あるいは **もっと見る** の後ろにある送信者、宛先、件名、日付、添付の絞り込みでメールボックス全体を探します。書いた相手から貯まる連絡先は、左欄のメールボックス設定の上に自分のページを持ちます。

## 6. メールボックスにアドレスを与える

メールボックスは、アドレスが向けられるまで何も受け取りません。ドメインの **エイリアス** タブで、種類に **メールボックスへ配送** を選び、自分のものを選んでひとつ追加します。パターン `^you$` で `you@example.com` が自分のものになります。同じタブが `hello@example.com` を別の場所へ転送する場所でもあるので、ひとつのドメインで両方できます。

## 7. 自分に送ってみる

別の場所のアカウントから `you@example.com` にメッセージを送ります。数秒のうちに受信箱に未読で入り、その数が左欄とタブのタイトルに出ます。開いて **返信** を押すと、返信は `you@example.com` からドメインの鍵で署名されて出ていき、控えが送信済みに残ります。

`hello@example.com` 宛のメールは、代わりに管理側のメール一覧に現れ、送信者の SPF、DKIM、DMARC の判定と、`--forward-to` に設定したアドレスへの配送の試行が表示されます。

届かなければ、キューのページが理由を示します。よくある原因を、答えである頻度の順に。

1. MX レコードがまだ伝播していない。`dig MX example.com` で確認します。
2. ポート 25 に外から到達できない。別の場所から `nc -vz mail.example.com 25` で確認します。
3. 転送先が拒否した。その場合キューにリモートサーバー自身の言葉が示されます。

## 8. メールプログラムで読む

メールプログラムは IMAP を話します。`listen.imaps` を設定するとサーバーはポート 993 でそれを提供します。compose ファイルはこのポートを公開し、これより前からあるサーバーでは、サーバー設定ページの **リスナー** タブが有効にする場所です。プログラムは自分のアドレスと **アプリパスワード** でサインインします。**メールボックス設定 → メールプログラム** でひとつ作り、デバイスの名前を付けて、表示されたパスワードをプログラムに入力してください。表示は一度きりです。同じタブに、プログラムが尋ねてくるもの——受信サーバー、ポート 587 の送信サーバー、ユーザー名——も並んでいますが、たいていのプログラムはアドレスから自分で見つけます。

## 次に

- **アドレスを増やす。** エイリアスは正規表現で照合するので、`^(sales|support)$` はひとつのエイリアスです。空のパターンはキャッチオールで、他のどれにも一致しなかったものを受け取ります。複数のエイリアスがひとつのメールボックスへ配送でき、メールボックスは自分のどのアドレスとしても送信できます。
- **人を増やす。** **管理 → 人とアクセス** が、アカウントとその所属グループをひとつのページで扱います。グループを選ぶと一覧がその members に絞られます。人は Members に入り、自分のメールボックスを読み書きします。あるいは Administrators に入り、すべてを管理します。ロールは編集でき、グループをドメインに結び付ければ権限はそこまでしか届きません。
- **自社の ID プロバイダーでサインインする。** **サーバー → シングルサインオン** は OpenID Connect の issuer と client を受け取ります。以後グループの *IdP グループ* がディレクトリに従い、people はそれが言うロールを持って現れます。
- **自分のデバイスから送る。** アプリパスワードはポート 587 からメールボックスのアドレスとして送ります。資格情報は——ドメインの設定ページにあり、送信元アドレスひとつに制限もできます——人ではなくドメインとして送るプログラムやスクリプトのためのものです。
- **ドメインを増やす。** 各ドメインは既定で自分の署名鍵を持ちます。ひとつを共有したいなら、`<selector>._domainkey` を CNAME で主ドメインに向けると、ダッシュボードが公開すべきレコードを示します。
- **[reference/deployment.md](https://github.com/ziyan/teanode/blob/main/docs/reference/deployment.md)** は同じサーバーを compose ファイルから動かすやり方で、アップグレード、バックアップ、起動しないときの対処を含みます。
- **[設定](/doc/configuration)** はすべての項目を記録しています。
- **[コマンドライン](/doc/command-line)** は CLI について。スキーマ全体に届き、繰り返す作業にはこちらが向いています。
