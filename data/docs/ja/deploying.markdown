TeaNode の動かし方は二つあります。ホストに二つのバイナリを置くか、コンテナイメージを使うか。どちらもリリースごとにビルドされ、どちらもダッシュボードを内蔵しているので、他に配備するものはありません。

[はじめる](/doc/getting-started)はバイナリの手順です。このページはコンテナについて、そしてどんな配備でも考えるべきこと、つまりサーバーと並んで動くもの、アップグレードの仕組み、バックアップの対象について書いています。

## イメージ

    docker pull ghcr.io/ziyan/teanode:latest

イメージにはサーバー、クライアント、ダッシュボードが入っていて、それ以外はありません。シェルもパッケージマネージャーもありません。root ではなく uid 65532 で動き、ポート 25、80、443、587 を bind するための `CAP_NET_BIND_SERVICE` だけを持ちます。

誰かが頼りにしているメールサーバーでは、`latest` を追いかけるのではなくバージョンを固定してください。アップグレードは、自分で選んだ日に自分でやることであるべきです。

## compose ファイル

リポジトリの [`deploy/docker-compose.yml`](https://github.com/ziyan/teanode/blob/main/deploy/docker-compose.yml) は完全な配備です。サーバー、PostgreSQL、そしてサーバーが使える任意のサービス。これと `.env` をどこかにコピーし、サーバーを記述して、起動します。

    mkdir -p /opt/teanode && cd /opt/teanode
    curl -LO https://raw.githubusercontent.com/ziyan/teanode/main/deploy/docker-compose.yml
    docker run --rm ghcr.io/ziyan/teanode:latest \
      teanode-server config env \
        --hostname mail.example.com --domain example.com > .env
    docker compose up -d

最初の起動の前に `.env` を編集してください。到達できる PostgreSQL（compose ファイルが `postgres:5432` に用意します）と、証明書の期限切れを認証局が知らせるためのアドレスが必要です。

サーバーはホストのネットワークを使います。接続してくるメールサーバーの本当のアドレスを見るためです。SPF は接続元アドレスを検査するので、ブリッジネットワークの後ろではすべての送信者が Docker のゲートウェイから来たように見え、SPF は無意味になります。

### 並んで動くもの

- **PostgreSQL** は設定、サーバーが扱ったメール、配送、DMARC レポート、使用量のカウンター、テンプレートを保持します。バックアップすべきものはこれです。
- **ClamAV** と **SpamAssassin** は任意のスキャナーで、compose ファイルでは既定で起動し、サーバーの設定では既定でオフです。要らなければサービスを削除し、設定はオフのままにしてください。ClamAV はシグネチャのために約 2GB のメモリを欲しがります。
- **MinIO** と **Redis** は複数のインスタンスを動かすときにだけ必要で、`cluster` プロファイルの中にあります。オブジェクトストアは生のメールの置き場所で、どのインスタンスが扱ったメールでもすべてのインスタンスが読めるようにします。Redis は途中まで進んだパスキーのサインインが待つ場所です。ロードバランサーの後ろでは、ブラウザーが最初のインスタンスに戻ってくる理由がないからです。

### データディレクトリ

`./data/teanode` は `/var/lib/teanode` にマウントされ、サーバーが書くもののうちデータベースにないすべてを持ちます。メールのスプール、使うなら GeoIP データベース、そしてステージングされたアップグレード。uid 65532 が読み書きできる必要があります。以前のバージョンを root で動かしていたサーバーではそうなっていません。

    chown -R 65532:65532 ./data/teanode

## アップグレード

ダッシュボードは六時間ごとにリリース一覧を確認し、最新バージョンをリリースノートとともに **設定 → サーバー** に表示します。そこからインストールすると、バイナリをダウンロードし、リリースのチェックサムで検証し、動いているものを置き換えて再起動します。

コンテナでは、新しいバイナリをイメージ内のものに上書きすることはできません。次の `docker compose up` でイメージは捨てられるからです。そこで代わりにボリューム上にステージングされます。compose ファイルが `/var/lib/teanode/upgrade` に設定する `TEANODE_UPGRADE_DIRECTORY` です。次の起動はそこから実行します。起動を終える前にクラッシュするリリースからは自動的に回復します。コンテナはイメージ内のバイナリを再び実行し、理由を告げます。

この変数を取り除いても何も壊れません。ダッシュボードからのアップグレードがオフになるだけで、`docker compose pull` はそのまま使えます。

自動アップグレードは既定でオフです。リリースはメールの扱いを変えることがあり、メールサーバーが足元で勝手に変わることを期待して導入する人はいないからです。`upgrade.automatic` でオンにし、`upgrade.window` で時間帯を制限できます。[設定](/doc/configuration#upgrade)を参照してください。

## 再起動が必要な設定

リスナー、TLS、オブジェクトストア、データディレクトリ、任意の連携は、プロセスの起動時に一度だけ読まれます。これらを変更すると、変更は保存されますが、インスタンスが再起動するまでそれ以上のことは起きません。ダッシュボードはそのことを告げ、古くなった設定の名前を挙げ、再起動を提案します。`teanode server restart` も同じです。

再起動とは、プロセスが終了し、それを監督するもの（コンテナの再起動ポリシー、または systemd）が新しいプロセスを起動することです。すでに受け付けたメールはディスク上にあり、後で配送されます。その数秒の間に接続してきた送信者は再試行します。

## バックアップするもの

データベースです。DKIM 署名鍵、すべての SMTP 資格情報のパスワードの元になるサーバーシークレット、セッション鍵、ACME アカウント鍵と証明書を含む設定が、メールと並んで入っています。

シークレットを含まないバックアップでは動くサーバーを復元できないので、もうひとつの形があります。

    teanode-server config export --file backup.yaml

これは設定全体を、シークレットも含めて、`config import` が読むのと同じ形式で書き出します。ファイルはあなただけが読めます。サーバーではない場所に置いてください。

ディスク上のメールスプールは `storage.spoolRetention` の期間だけ保持されて削除されます。ここ数日のメール本文が惜しいのでなければ、バックアップする価値はありません。

## 複数のインスタンス

複数のインスタンスをひとつのデータベースに対して動かせます。設定は PostgreSQL で、保存したメールはオブジェクトストアで、途中まで進んだパスキーのサインインは Redis で共有します。それぞれに固有の `TEANODE_INSTANCE_ID` を与えてください。使用量カウンターを積み上げるキーの一部で、同じ名前を共有する二つのインスタンスは互いのカウントを失います。

    docker compose --profile cluster up -d

で MinIO と Redis も一緒に起動します。同時に `.env` の `TEANODE_S3_*` ブロックのコメントを外してください。そこにある資格情報は MinIO の起動に使うものと同じです。接続するのはサーバーだからです。
