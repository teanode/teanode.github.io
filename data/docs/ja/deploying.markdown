TeaNode の動かし方は二つあります。コンテナイメージか、ホストに置いた二つのバイナリか。どちらもリリースごとにビルドされ、どちらもダッシュボードを含むので、他に配備するものはありません。

[クイックスタート](/doc/quick-start)は四つのコマンドでコンテナを動かします。このページは compose ファイルの中身、サーバーのアップグレード、バックアップの対象についてです。[はじめる](/doc/getting-started)はバイナリの手順です。

## イメージ

    docker pull ghcr.io/ziyan/teanode:latest

イメージにはサーバー、クライアント、ダッシュボードが入っていて、それ以外はありません。シェルもパッケージマネージャーもありません。root ではなくユーザー 65532 で動き、ポート 25、80、443、587 を bind するための `CAP_NET_BIND_SERVICE` だけを持ちます。

人が頼りにしているサーバーでは、`latest` を追いかけるのではなくバージョンを固定してください。アップグレードは自分で決めてやることであるべきです。

## compose ファイル

リポジトリの [`deploy/docker-compose.yml`](https://github.com/ziyan/teanode/blob/main/deploy/docker-compose.yml) は完全な配備です。サーバー、PostgreSQL、そして任意のサービス。`.env` の隣にコピーし、サーバーを記述して、起動します。

    mkdir -p /opt/teanode && cd /opt/teanode
    curl -LO https://raw.githubusercontent.com/ziyan/teanode/main/deploy/docker-compose.yml
    docker run --rm ghcr.io/ziyan/teanode:latest config env --output - \
      --hostname mail.example.com --domain example.com > .env
    chmod 600 .env
    docker compose up -d

最初の起動の前に `.env` の `TEANODE_TLS_ACME_EMAIL` を設定してください。証明書の期限が近づいたときに認証局が知らせるアドレスです。

ポート 80 はインターネットから届く必要があります。認証局がそこにチャレンジを置くからです。ポート 80 はそのチャレンジに答え、それ以外はすべて HTTPS へ送ります。ダッシュボードが平文で提供されることはなく、応答は `Strict-Transport-Security` を伴うので、一度ここに来たブラウザは平文の HTTP を二度と試みません。

サーバーは Docker のネットワークではなくホストのネットワークを使います。SPF はメールサーバーが接続してきたアドレスを検査するので、Docker のブリッジの後ろではすべての送信者が Docker のゲートウェイから来たように見えてしまいます。

PostgreSQL への接続は暗号化され、検証されます。公式の PostgreSQL イメージは TLS を提供しないので、compose ファイルが証明書を生成して PostgreSQL をそれで起動し、`config env` が書く `TEANODE_DATABASE_URL` はその証明書に対して `sslmode=verify-full` を求めます。自前の PostgreSQL を指すなら、`sslrootcert` をそのサーバーの認証局に向けるか、誰が応答したかを確かめずに暗号化だけする `sslmode=require` に下げてください。

### 並んで動くもの

- **PostgreSQL** は設定と、サーバーが扱ったすべて、つまりメール、配送、DMARC レポート、使用量のカウンター、テンプレートを保持します。バックアップするのはこれです。
- **ClamAV** と **SpamAssassin** はウイルスとスパムを検査します。compose ファイルは起動しますが、設定でオンにするまでサーバーは使いません。要らなければファイルからサービスを削除してください。ClamAV は約 2GB のメモリを必要とします。
- **MinIO** と **Redis** は複数のインスタンスを動かすときだけのもので、`cluster` プロファイルの中にあります。MinIO は生のメールを保持し、どのインスタンスが受け取ったものでもすべてのインスタンスが読めるようにします。Redis は途中まで進んだパスキーのサインインを保持します。ロードバランサーの後ろでは、二つ目のリクエストが一つ目とは別のインスタンスに届くことがあるからです。

### データディレクトリ

`./data/teanode` は `/var/lib/teanode` にマウントされ、サーバーがデータベースの外に書くもの、つまりメールのスプール、使うなら GeoIP データベース、ステージングされたアップグレードを保持します。ユーザー 65532 が読み書きできる必要があります。以前のバージョンを root で動かしていたなら、ディレクトリは root の所有でサーバーは読めません。一度だけ直してください。

    chown -R 65532:65532 ./data/teanode

## アップグレード

ダッシュボードは六時間ごとに新しいリリースを確認し、最新のものをリリースノートとともに **設定 → サーバー** に表示します。そこからインストールすると、バイナリをダウンロードし、リリースのチェックサムで確かめ、動いているバイナリを置き換えて再起動します。

コンテナでは、新しいバイナリをイメージ内のものと置き換えることはできません。次の `docker compose up` でイメージは捨てられるからです。代わりにボリューム上の、`TEANODE_UPGRADE_DIRECTORY` が指すディレクトリに保存され、次の起動はそこから実行します。新しいリリースが起動に失敗すると、コンテナはイメージ内のバイナリに戻り、理由を報告します。

この変数は取り除けます。その場合ダッシュボードからのアップグレードは使えなくなり、`docker compose pull` がアップグレードの方法になります。

自動アップグレードは既定でオフです。リリースはメールの扱いを変えることがあり、メールサーバーはあなたの知らないうちに変わるべきではありません。`upgrade.automatic` でオンにし、`upgrade.window` で時間帯を制限できます。[設定](/doc/configuration#upgrade)を参照してください。

## 再起動が必要な設定

リスナー、TLS、オブジェクトストア、データディレクトリ、任意のサービスは、プロセスの起動時に一度だけ読まれます。これらを変更すると変更は保存されますが、インスタンスが再起動するまで効果はありません。ダッシュボードはどの設定が待っているかを示し、再起動を提案します。`teanode server restart` も同じです。

再起動とは、プロセスが終了し、それを監督するもの、つまりコンテナの再起動ポリシーか systemd が新しいプロセスを起動することです。すでに受け付けたメールはディスク上にあり、あとで配送されます。その数秒の間に接続してきた送信者は再試行します。

## バックアップするもの

データベースです。メールとともに、設定とシークレット、つまり DKIM 署名鍵、すべての SMTP パスワードの元になるサーバーシークレット、セッション鍵、ACME アカウント鍵と証明書を保持しています。

ファイルの形もあります。

    teanode-server config export --file backup.yaml

これは設定全体をシークレットも含めて、`config import` が読む形式で書き出します。ファイルはあなただけが読めます。サーバー以外の場所に置いてください。

ディスク上のメールスプールは `storage.spoolRetention` の期間だけ保持されて削除されます。ここ数日のメール本文しか持たないので、ふつうはバックアップする価値はありません。

## 複数のインスタンス

複数のインスタンスをひとつのデータベースに対して動かせます。設定は PostgreSQL で、保存したメールはオブジェクトストアで、パスキーのサインインは Redis で共有します。それぞれに固有の `TEANODE_INSTANCE_ID` を与えてください。使用量カウンターを保存するキーの一部で、同じ名前の二つのインスタンスは互いのカウントを上書きします。

    docker compose --profile cluster up -d

で MinIO と Redis も起動します。同時に `.env` の `TEANODE_S3_*` ブロックのコメントを外してください。そこにある資格情報は MinIO の起動に使うものです。
