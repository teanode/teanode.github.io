这是对 TeaNode 现状的一次审查，写给正在决定是否把它放到公网上运行的人，让他们能看到检查了什么、发现了什么，以及有意没有检查什么。

## 1. 摘要

十项发现，其中八项已修复。有一项确实要紧：一次被拒绝的 SMTP 认证把一份可用的凭据写进了日志。

一个邮件服务器中分量最重的那些控制都站得住。它不是开放中继；聚合流水线不能被用来注入 SQL；模板化的主题行不能注入邮件头。这些现在每一条都由测试断言，而不是靠相信。

还未解决的属于加固而不是缺陷，只有一项：`X-Forwarded-Proto` 对任何调用者都被采信（SEC-7，已在第二次审查中修复）。认证已有速率限制，ACME 重试循环已有上限，容器以非 root 用户运行，依赖的积压——43 个可触达的漏洞，其中一个是认证前的拒绝服务——已经清空。

## 2. 范围

### 在范围内

- 25 端口上的 SMTP 服务器，无需认证，任何人可达
- 587 端口上的提交，用凭据认证
- 80/443 端口上的仪表盘和 GraphQL API
- `POST /api/v1/send/{domain}/{template}`，用凭据认证；认证中间件按路径前缀放行，由处理器自己检查
- GraphQL 中的 `SendMail`、`RenderTemplate` 和 `RenderLayout`，仅限运维者，它们以已配置的域名发信并渲染运维者写的模板
- 人和机器的身份认证与会话处理
- 配置文件，以及 API 从中泄露的内容
- SQL 构造，包括聚合流水线
- 邮件解析与渲染，包括仪表盘的邮件视图
- 依赖，通过 `govulncheck`

### 不在范围内

- 主机、它的防火墙和容器运行时
- PostgreSQL 自身的配置和它的网络暴露
- ClamAV 和 SpamAssassin，它们按配置被信任
- 服务器所用的 DNS；假定不存在恶意解析器
- 靠流量堆出的拒绝服务，区别于算法复杂度导致的
- 对 DKIM、ARC 和 SPF 实现的正式密码学审查
- 某个具体部署的 DNS 记录是否正确，这是仪表盘的工作，不是本审查的

### 假设

- 运维者是被信任的。这是单租户软件：一个通过认证的仪表盘用户就是管理员，让管理员访问自己网络的功能是设计，不是缺陷。
- 存储配置中的服务器密钥是保密的。每一份 SMTP 凭据都由它派生，所以它的泄露意味着提交功能的彻底沦陷。
- 到达 25 端口的邮件完全是敌意的。

## 3. 信任边界

| 边界 | 对面是谁 | 信任什么 |
| --- | --- | --- |
| 25 端口 | 互联网上的任何人 | 什么都不信 |
| 587 端口 | 持有凭据的人 | 凭据，对照服务器密钥验证 |
| 80 端口 | 任何人 | 什么都不信；提供 ACME 挑战和重定向 |
| 443 端口 | 任何人，然后是会话或令牌 | 会话 cookie 的 HMAC，或令牌的哈希 |
| `/api/v1/send` | 持有凭据的人 | 同 587 |
| 配置文件 | 运维者 | 完全信任 |
| PostgreSQL | 运维者自己的网络 | 完全信任 |
| ClamAV、SpamAssassin | 运维者自己的网络 | 完全信任 |
| 外发 SMTP | 远端服务器 | 什么都不信 |

要紧的那条线在 25 端口和 587 端口之间。所有决定这台服务器是否会替第三方送信的东西都在这条线上。

## 4. 发现

### SEC-1——一次被拒绝的登录打印了一份可用的密码（高，已修复）

`security.DecodeCredential` 用提交的密码*和*本该被接受的密码构造错误信息，而每个调用者在 SMTP 认证失败时都以 error 级别记录这个错误。

客户端选择密码的前十六个字符；服务器用服务器密钥从中派生出剩下的十六个。所以这条日志不是泄露了一个已有的密码，而是服务器把客户端提供的任何前缀补全了。一次被拒绝的登录，加上对日志文件、支持包或备份的读权限，就产生了一份可用的凭据。

`security.DecodeToken` 也是同样的形状。一次成功的认证还以 debug 级别记录了凭据密钥。

在 `4b6ceb9` 中修复：两者都返回一个不说明任何内容的哨兵错误，debug 行去掉了密钥，`internal/util/security/disclosure_test.go` 断言没有任何错误文本包含尝试的密码、本该可用的密码，或它派生出的那一半。

### SEC-2——密钥逐字节比较（低，已修复）

上面两处比较都对字符串使用 `!=`，它在第一个不同的字节处停止。由于攻击者控制输入的一部分而服务器派生其余部分，这是对派生那一半的时序预言机。跨网络的远程时序攻击很难；修复只有一行。两者现在都用 `subtle.ConstantTimeCompare`。在 `4b6ceb9` 中修复。

### SEC-3——依赖落后了 43 个已知漏洞（高，已修复）

`govulncheck` 报告了 43 个这段代码确实会触达的漏洞。三十三个在标准库里，对应固定在 Go **1.25.0** 的构建；其余在五个模块里。

有一个值得单独指出。**GO-2025-4006**，`net/mail.ParseAddress` 中过高的 CPU 消耗，可以从 `mailparse.ParseAddress` 触达，而 `handleRcpt` 对每个 `RCPT TO` 中的地址都调用它——在认证之前，任何能连上 25 端口的人都可以。那是程序最暴露的表面上的一个认证前算法拒绝服务。

`go` 指令现在要求 **1.25.14**，它超过了 govulncheck 点名的每一个标准库修复，五个模块也向前推进：

    golang.org/x/net                v0.42.0 -> v0.58.0
    golang.org/x/text               v0.27.0 -> v0.41.0
    github.com/jackc/pgx/v5         v5.7.5  -> v5.9.2
    aws-sdk-go-v2/service/s3        v1.86.0 -> v1.97.3
    aws-sdk-go-v2/.../eventstream   v1.7.0  -> v1.7.8

扫描现在报告 **0 个可触达的漏洞**。还剩一个在一个被依赖但从未被调用的模块里——`golang.org/x/crypto` 中的 GO-2026-5932——尚未发布修复版本。

工作流和 Dockerfile 都不需要改：`go-version: '1.25'` 和 `FROM golang:1.25` 本来就跟随最新的补丁版本，而 `go.mod` 里的下限是让旧工具链大声失败而不是悄悄构建的东西。镜像被重新构建以确认它报告 `go1.25.14`，而不是假设如此。

`npm audit --omit=dev` 报告仪表盘没有漏洞。

### SEC-4——没有任何东西对认证限速（中，已修复）

SMTP `AUTH` 和仪表盘登录都没有节流、锁定或退避，所以两者都可以以线速猜测。仪表盘碰巧有一点保护——高于默认代价的 bcrypt 让每次尝试都昂贵——但这个代价服务器同样要付，这正是应该尽早拒绝而不是依赖哈希很慢的理由。SMTP 凭据没有这种巧合：验证只是一个 HMAC 和一次比较。

两者现在都按地址用令牌桶限制，默认一次二十次尝试，之后每分钟十次，可通过 `smtp.authRateLimit` 和 `smtp.authRateBurst` 调整。

其中两个选择值得说明，因为任何一个弄错都会让限制形同虚设：

- **按地址计，而不是按账户或凭据。** 猜测中的身份由猜测者选择，所以按身份计数让他们换个身份就能重置计数。出于同样的原因，键里去掉了端口——否则一个新连接就是一个新桶。
- **一个桶只有在重新装满之后才会被遗忘。** 注册表必须淘汰，因为键是远端地址，而一个拥有 /64 的攻击者拥有的地址比这个进程拥有的内存还多。满的桶和从未存在过的桶无法区分，所以丢掉它不会宽恕任何东西；丢掉一个被抽干的桶则会为抽干它的人清除限制。达到键数上限时，调用者拿到的是一个不被保留的桶而不是没有桶，所以他们仍然受限。

### SEC-5——ACME 重试循环没有上限（中，已修复）

失败的订单会被重试，没有退避也不会放弃。一个无法验证的名字——80 端口不可达的域名，这是这里最常见的失败方式——每五分钟被重试一次，永不停止，然后撞进 Let's Encrypt 的验证失败速率限制，并一直停在那里。在每个域名一张证书的情况下，这比噪音更糟：一个坏掉的名字花光了其他所有名字需要的额度。

每张证书现在带有自己的失败计数和下次尝试时间：`requestBackoff` 从五分钟开始，翻倍直到一天（`internal/util/autoacme/autoacme.go`）。开始工作的名字在一天内会被重试；永远不工作的名字每天花费一次尝试，别无其他。

### SEC-6——容器以 root 运行（低，已修复）

`deploy/Dockerfile` 没有设置 `USER`，而 `gcr.io/distroless/static-debian12` 默认是 root。绑定 25、80、443 和 587 需要特权，而进程之后从未放弃它。

值得记录的是这是一次退步而不是长期的弱点：被替换的那套部署本来就以非特权的 `nobody` 运行。重构重写容器定义时丢掉了这一点，没有人注意到，因为没有任何东西检查。

用 `:nonroot` 标签修复，它以 uid 65532 运行，加上两个 compose 文件里的 `CAP_NET_BIND_SERVICE`。这项能力就是 root 被用到的全部，所以只授予它严格小于授予 root。代码没有改动。部署测试以非 root 通过，包括绑定 25 端口并在其上接收邮件。

对升级的人有一个后果：挂载的配置目录和数据目录是由以 root 运行的进程创建的，uid 65532 读不了它们。启动新镜像之前，对两者做一次 `chown -R 65532:65532`。compose 文件这样说，入门指南也这样说。

### SEC-7——`X-Forwarded-Proto` 对任何人都被采信（低，已修复）

`isSecureRequest` 相信这个头，没有可信代理列表。危险的方向不是伪造——客户端声称 `https` 只会得到一个*更*严格的 cookie——而是缺失：在一个不设置该头的 TLS 终结器后面，会话 cookie 被签发时没有 `Secure`，并会通过明文发送。

在第二次审查中修复（SEC-20）：现在只有来自 `server.trustedProxies` 里列出的代理时才采信这个头，和 `X-Forwarded-For` 同一条规则；而自己终结 TLS 的服务器会把明文监听器重定向到 HTTPS 并发送 `Strict-Transport-Security`，这就为本项目发布的那种部署关上了「缺失」这一路。

### SEC-8——Webhook 别名能到达运维者指向的任何地方（信息）

`webhook` 类型的别名让服务器把邮件 POST 到配置的 URL。URL 只被校验为 http 或 https，别的不管，所以管理员可以把它指向一个私有地址。这是被接受的：管理员本来就能把邮件转发到任意主机。值得知道的是 `sendWebhook` 使用 `http.DefaultClient`，它自身没有超时并且会跟随重定向，所以完全依赖上下文的截止时间。

### SEC-9——服务器被认领之前 API 是开放的（中，已修复）

配置中没有用户时，`requireOperator` 返回 nil。这让引导成为可能——第一个账户必须能由还不能登录的人创建——但它开放的是整个 API，而不只是引导用的 mutation。

在第一次启动和第一个账户被创建之间，任何能连上服务器的人都可以通过 `ListDomains` 等读取配置，然后调用 `CreateFirstAccount` 把它据为己有。在一台用 `config init` 启动的服务器上，已经有一个域名、它的别名和它的 DKIM 选择器可读。

部署手册通过让运维者提前认领服务器来绕过这个问题，这对那套部署是对的，但对其他任何人都不是修复。

通过删除这个豁免来修复。`GetSession`、`CreateFirstAccount`、`Login` 和 `Logout` 从不调用 `requireOperator`，所以认领服务器仍然可行；其余一切现在都拒绝匿名调用者，无论账户是否存在。`teanode user add --offline` 直接写配置文件，不受影响，切换手册用的正是这条路。

`TestEveryOperationAuthorises` 已经断言每个解析器都做授权，它自己的注释还声称每一个"没有运维者时会拒绝"——在这次改动之前那并不成立。这个行为现在有了自己的测试放在旁边。

发现它是因为部署测试框架中的一个检查断言的是空字符串，它匹配任何回复，所以无论服务器怎么表现都通过。

### SEC-10——未知的 API 路径回答 401，从不回答 404（信息）

认证在路由之前运行。在任何账户存在之前，路径会落到仪表盘并返回带 HTML 的 200，这正是让部署测试的失败无法阅读的原因。

### SEC-11——邮箱、应用专用密码、IMAP 和单点登录（信息）

随邮箱这一系列工作加入（[`docs/planning/active/20260906-mailboxes.md`](https://github.com/ziyan/teanode/blob/main/docs/planning/active/20260906-mailboxes.md)），并且是边做边审查，而不是事后：

- API 里每一个邮箱、文件夹和条目操作都会解析出对应的行，并在调用者不是邮箱所有者时拒绝（`internal/api/v1api/apigraph` 中的 `requireMailbox`、`requireFolder`、`requireItems`）；一封邮件的内容只有它所在邮箱的所有者，或者对它的域名持有 `mail:audit` 的人才能读（`access.CanReadMail`）。拒绝一律回答"不存在"。
- 应用专用密码是 32 个字母表里的二十个字符，用 bcrypt 哈希，只显示一次，可以单独吊销，而且永远不是账户密码。IMAP 和提交端口的登录走的是与凭据相同的按地址速率限制，而各种出错方式只有同一个答复。
- 在连接加密之前，IMAP 会通告 `LOGINDISABLED`；993 端口从第一个字节起就是 TLS。用应用专用密码登录的提交，如果发件人不是这个邮箱自己的地址之一，会被拒绝。
- 现在只有在 `reject` 策略下 DMARC 失败才会被拒绝；`none` 和 `quarantine` 会被记录，被隔离的邮件落进垃圾邮件文件夹，垃圾邮件过滤器给这次失败打分。这比以前宽松，也正是策略所要求的。
- 单点登录使用带 PKCE 和 nonce 的授权码流程，state 用服务器密钥签名并在十分钟后过期，issuer 必须是 `https` 且其发现文档必须写着它自己，HTTP 客户端拒绝连接私有、回环或链路本地地址，无论什么名字解析到它。client secret 在 API 里只写不读。身份提供商的群组只会影响那些写明了它的群组。
- 交给提供商的回调地址由 `Host` 和 `X-Forwarded-Proto` 构造，所以 SEC-7 对它同样适用。
- 草稿的文件以 multipart 主体上传到 `PUT /api/v1/mailbox/drafts/{itemId}/attachments` 或 `POST /api/v1/mailbox/{mailboxId}/drafts/attachments`，需要认证（一个会话或一个 bearer 令牌），邮箱的归属按 GraphQL 草稿解析器同样的方式检查。这个检查在读取请求体*之前*、在一个短事务里进行，所以陌生人的请求不会带来任何缓冲开销，写入草稿时再检查一次。请求体由 `http.MaxBytesReader` 按邮件大小上限截断，并逐个文件再计一次（超过则 413）；这些文件随后加入草稿已有的部分，总量超限则作为无效拒绝（400）。没有配置邮件大小上限时，上传不设上限，和 SMTP 一样。过期的草稿 id 会被拒绝。回复是存储后的草稿，所以页面永远不用猜某一部分的序号。
- `ApplyMailboxRules` 把一个邮箱已存的规则跑在已经归档的文件夹上，就像到达时对新邮件那样。它通过带 `mail:write` 的 `requireMailbox` 解析邮箱，通过 `requireFolder` 解析文件夹，并把属于另一个邮箱的文件夹当作不存在来拒绝。一页上限 500 封；移动到已经消失或属于别处的文件夹不做任何事；`delete` 是移到回收站而不是抹掉；`forward` 会被计数并跳过，所以这个变更不可能把旧邮件重新发到规则指定的地址。`mail:send` 被刻意不去查，因为没有任何东西离开服务器。
- `ListMailboxItems` 的搜索筛选（`from`、`to`、`subject`）作为参数到达 `ILIKE`，调用者输入里的 `%`、`_` 和 `\` 会先被转义；`since`/`before` 是带类型的，分页也有上限。`SaveMailboxContact`、`DeleteMailboxContact` 和 `SetMailboxFolderPinned` 走与邮箱 API 其余部分相同的归属检查，最后一个还会拒绝收件箱，因为它一直在最上面。

未解决：IMAP 服务器还没有通告 CONDSTORE 或 QRESYNC，所以客户端同步一个大文件夹时走的是慢路径。

## 5. 已验证的控制

这些经过检查并被认为可靠。存在测试的地方，写明了测试的名字。

### 5.1 它不是开放中继

替第三方送信要求设置 `envelope.CredentialID`、`envelope.DomainID` 或 `envelope.MailboxID`（`internal/mx/exchange.go`）。SMTP 服务器设置 `CredentialID` 或 `MailboxID`，而且只在完成 `AUTH` 之后；`DomainID` 只能从内部发送路径到达。带 `MailboxID` 的提交还会被进一步拒绝，除非发件人是那个邮箱的地址之一，并且它的所有者持有 `mail:send`。

因此未认证的邮件走 `handleIncoming`，它要求收件域名是配置服务的域名之一，否则回答"mailbox unavailable"（`internal/mx/exchange_incoming.go:39`）。

`handleOutgoing` 对照配置重新验证凭据的密钥，而不是相信 `AUTH` 发生过，并拒绝被限制为某个本地部分的凭据以另一个身份发信。

### 5.2 聚合流水线不能携带 SQL

字段名以标识符的形式进入语句，无法参数化，所以唯一的防御是名字必须是表提供的——`Columns.resolve` 里的一次 map 查找。值总是进占位符。排序方向是由分支选择的字面量 `ASC` 或 `DESC`，从来不是调用者的文本，并且还对照一个封闭集合校验。

由 `internal/util/aggregate/injection_test.go` 断言，它对筛选、排序和去重尝试八个敌意字段名，并确认敌意的*值*作为参数携带而不是被拒绝。

### 5.3 模板化的主题不能注入邮件头

发送 API 把调用者提供的变量渲染进模板的主题。每个值都经过 `EncodeHeaderValue`，它做 RFC 2047 base64 编码，所以 `\r\n` 成为编码词的一部分，从不以字面形式出现。用四个 CRLF 载荷探测过。

信封地址单独用 `mail.ParseAddress` 解析，只使用解析出的 `Address`，所以显示名也偷运不了任何东西。

### 5.4 静态存储的凭据

- 人的密码：bcrypt，高于默认代价，在存储的配置中。
- API 令牌：来自 `crypto/rand` 的 32 字节，以秘密那一半的 SHA-256 存储，用 `subtle.ConstantTimeCompare` 比较。明文只显示一次，从不存储。
- SMTP 凭据：由服务器密钥经 HMAC-SHA256 派生，所以配置里没有可偷的密码——但这个密钥等价于全部凭据。
- GraphQL 层脱敏所有标记为 `secret:"true"` 的东西，涵盖服务器密钥、AWS 凭据、令牌哈希和密码哈希。

### 5.5 会话处理

cookie 是 `HttpOnly`、`SameSite=Lax`，并在请求是 TLS 时为 `Secure`（受 SEC-7 影响）。它的值是对用户名和过期时间的 HMAC，以恒定时间验证。`SameSite=Lax` 是挡在 GraphQL 端点和跨站请求伪造之间的东西，因为跨站 POST 不携带 cookie。

### 5.6 渲染的邮件

邮件在受限 CSP 下的沙箱 iframe 中渲染。脚本不会运行。远程图片和 `cid:` 引用被阻止，这就是内联图片显示为空白的原因。CSS 被保留——有意的，让邮件看起来像邮件——但去掉了 `@import`、`expression(`、`behavior:` 和 `-moz-binding`。

## 6. 接受的剩余风险

- **服务器密钥是提交功能的单点致命故障。** 每一份 SMTP 凭据都由它派生。不存在不会一次性使所有凭据失效的轮换路径。
- **管理员可以通过 webhook 别名和转发目标访问内部网络。** 单租户软件；管理员是被信任的。
- **DNS 被信任。** SPF、DKIM 和 DMARC 验证相信解析器。不验证 DNSSEC。
- **没有审计日志。** 没有记录谁改了配置里的什么。

## 7. 接下来做什么

1. 添加可信代理设置，或者只要配置了 TLS 就默认开启 `Secure`（SEC-7；已在第二次审查中完成）。
2. 定期重新运行 `govulncheck`。它找到了四十三件没人找过的事；还会找到更多。
3. 给配置加审计日志。没有任何东西记录谁改了什么。

## 8. 本次审查没有做的

没有对 MIME 和邮件头解析器做模糊测试，而邮件服务器剩下的内存和复杂度 bug 通常就藏在那里。除已有测试外，没有对照规范审查 DKIM、ARC 和 SPF 的实现。没有对运行中的实例做渗透测试。没有依赖许可证审计。在把它推荐给其他任何人之前，每一项都值得做。

## 摘要

三十四项发现，其中二十九项在此修复。其中五项要紧：

- 一旦一个人可以改自己的账户名，他就可以把名字改成控制台的名字，并从下一个请求起
  持有全部权限（SEC-33）。
- 一个域名的管理者可以读取、改写和删除另一个域名的模板与布局，一个审计者可以重发
  另一个域名的投递（SEC-13）。
- 一份限定到单个地址的凭据，可以以它所在域名的任何地址发信，并且是签名过、对齐的
  （SEC-14）。
- SPF 的 `ptr` 机制会对发信方反向区域声称的任何名字通过，这对每一个使用它的域名都是
  一次 DMARC 绕过（SEC-15）。
- 四条路径，让任何人从 25 端口发来的一封邮件消耗服务器数小时的 CPU 或无上限的内存
  （SEC-16 到 SEC-19）。

仍未解决的是对发布流水线的信任（SEC-31）、compose 文件自带的数据库密码（SEC-32），
以及记在末尾的三件小事。

## 发现

### SEC-12——二十二个可触达的标准库漏洞（高，已修复）

对 Go 1.26.0 跑 `govulncheck`，报告了 22 个这份代码能触达的标准库漏洞，其中包括从
passkey 登录触达的 `crypto/x509` 证书检查中的 panic，以及 `net/mail`、`net/textproto`、
`mime` 和 `net/url` 里的解析错误，全部在 1.26.6 修复。`go` 指令现在是 `1.26.6`，这也是
第一次审查选择的同一种强制方式，扫描现在报告为零。每周的工作流会在下一个周一发现它们。

### SEC-13——按「某个域名」而不是按行自己的域名判权（高，已修复）

`GetTemplate`、`DeleteTemplate`、`GetLayout`、`ModifyLayout`、`DeleteLayout`、
`GetDelivery`、`RetryDelivery`、`ListDeliveriesByMail`、`GetReport`、`GetMailOpens`
和 `ListMailOpens` 只检查调用者在*某个*域名上持有 `domain:manage` 或 `mail:audit`，
然后就去读被指名的那一行。标识符不是秘密。一个在某个域名上被授予 `domain:manage` 的
群组——而这正是这种权限的用途——可以把另一个域名的布局改写成一个钓鱼页面，此后经由它
渲染的每一个模板都会带上它；可以删掉那个域名的模板，读它投递的收件人和错误文本，并
重新触发一次失败的投递。`ModifyTemplate` 做对了，这反而显出了本该有的写法。

现在每一个都在加载之后对该行自己的域名调用 `requireDomainPermission`，对调用者不持有的
域名和已被删除的域名都回答「未找到」，所以别的什么都没有变。`ListMailOpens` 过滤到调用者
可审计的域名。由 `TestRowsAreScopedToTheDomainThePermissionIsHeldOver` 断言。

`TestEveryOperationAuthorizes` 没有抓到这个，因为它检查的是每个解析器里有没有出现某个
辅助函数的*名字*，而不是这个辅助函数被问了什么。

### SEC-14——受限凭据可以以域名下任何地址发信（高，已修复）

凭据的 `alias` 限制——那个让运维者可以交给一个订阅信服务一份只能以 `newsletter@` 发信的
凭据的东西——只作用在信封发件人上。收件人真正读到的 `From` 头被解析、被存下，却从不比对。
随后这封邮件被为该域名做了 DKIM 签名并标为 `auth=pass`，所以这次冒充是对齐并且通过认证的。
邮箱的提交路径本来就两个都检查，现在凭据路径也这么做（`credentialMaySendAs`）。不受限的
凭据没有变化。

### SEC-15——SPF `ptr` 接受任何能解析的名字，并按裸后缀匹配（高，已修复）

RFC 7208 §5.5 只在一个 PTR 名字能解析回连接地址时才认可它；这个求值器保留了任何能解析到
任何东西的名字。谁控制一个地址的反向区域，谁就决定它声称的名字，所以一个发信方把自己的
PTR 设成 `www.victim.example`，`ptr` 就为受害者的域名通过了。`ptr:example.test` 还会匹配
`notexample.test`，没有标签边界。两者都已修复，各有测试数据；一份依赖旧有宽松行为的既有
测试数据也被更正了。

### SEC-16——邮件头展开是平方级的（高，已修复）

`mailparse.Split` 把每一个续行追加到它所属的头字符串上，每次都复制整个头。两兆字节的
` x` 行要花一分多钟，而代价按平方增长；允许的最大邮件就是一天的 CPU，而 `Split` 在任何
检查之前就对每封邮件运行——不需要有被服务的域名，只需要一个连接。头块现在用 builder 构建，
并限制为 4096 个头、每个 64 KiB，超过就拒收这封邮件。DSN 解析器里同样的循环也用同样的
办法修好了。

### SEC-17——多部分嵌套没有上限（高，已修复）

`TraverseParts` 无限制地递归穿过嵌套的多部分正文，每一层都是一个包在上一层外面的 reader，
所以在深度 N 处读一个字节要穿过 N 个 reader。一层对发信方来说值五十字节；一封嵌套两万层的
邮件要花掉将近一分钟，嵌套一百万层的要好几天。接收时为内容和病毒检查触达，来自任何能给
被服务域名发信的人，在仪表盘里还会再触达一次。现在限制为 32 层。

### SEC-18——DMARC 汇总报告的接收没有上限（高，已修复）

`rua` 地址发布在每个域名的 DMARC 记录里，所以任何人都能往那里发，而且到达的东西不经过任何
认证检查。里面的报告被无限制地解压——一兆字节的 gzip 就是一吉字节的记录——每一条记录都变成
一行，而其中每一个不同的来源地址都会被反向解析，一次一个，每个五秒，全都在那个还开着的
事务里，甚至在看这份报告属于哪个域名之前。

现在：解码后的报告限制为 16 MiB 和 10000 条记录，一个 zip 限制为 16 个文件；报告寄到的地址
会被解析成「以它为报告地址的那个域名」，写给任何别的域名的报告在做任何工作之前就被丢掉；
最多解析 256 个地址，一次八个，全部在三十秒之内。由 `TestAnAggregateReportIsBounded` 断言。

### SEC-19——DKIM 签名、命令行和连接都没有上限（高，已修复）

25 端口缺的三个上限：

- 每一个 `DKIM-Signature` 头都会被验证，各自一个 goroutine、各自一次密钥查询、各自对整个
  正文做一次哈希。一封邮件可以带一百万个。现在最多检查八个，这是 RFC 6376 §6.1 允许的；
  正文哈希按规范化方式各算一次，`h=` 列表有上限，而一个 panic 的 goroutine 仍会作答，
  所以验证器不会永远等下去。
- 一行命令会一直读到换行到达为止，无论要多久；一个从不发送换行的客户端会按线路速率被缓冲
  到读取超时。现在超过 8 KiB 的行会以 `500 5.5.2` 被拒绝。
- 连接没有上限，每一个都是一个 goroutine，而且一旦它发出 DATA，就是一块和最大邮件一样大的
  缓冲区，最长可以持续一个小时。现在每个监听器同时服务 1000 个，超过就回答 `421`。处理一封
  已接受的邮件限制在十分钟内。

GraphQL 端点在认证之前就可以触达，因为登录本身是一个 mutation，它现在把请求体限制为
1 MiB，而两个 HTTP 监听器都有了头部、读取和空闲超时。

### SEC-20——仪表盘在 80 端口以明文提供（中，已修复）

80 端口回答 ACME 质询，然后把整个仪表盘和 API 都提供出去。在浏览器里敲一个主机名，先到的
就是那里，而在那里登录的读者会以明文发出密码，并收到一个没有 `Secure` 的 cookie，此后浏览器
就一直那样发送它。当这个进程自己提供 HTTPS 时，明文监听器现在会把除质询路径以外的一切以
`308` 重定向过去；而在一个终结 TLS 的代理后面、这里没有 HTTPS 监听器时，它照旧提供服务。
经由 TLS 的响应带上 `Strict-Transport-Security`。`X-Forwarded-Proto` 只有来自列出的代理时
才被采信（SEC-7），这一点用在会话 cookie、单点登录 cookie 和交给身份提供方的重定向地址上。

### SEC-21——两个 `From` 头（中，已修复）

DMARC 在最后一个 `From` 头上求值，而邮件程序显示第一个，所以一封在最后一个头里由攻击者
自己的域名签名、在第一个头里指名受害者的邮件，会通过 DMARC 并显示为受害者。RFC 7489
§6.6.1 说这样的邮件应当拒收；现在它会以 invalid-From 错误被拒收。

### SEC-22——`<noscript>` 把标记带过了清理器（中，已修复）

清理器在开启脚本的模式下解析邮件，而在那个模式下解析器会把 `<noscript>` 里面的东西当作
一整块文本保留，并原样写回去。显示邮件的框架是不跑脚本的，所以浏览器把那段文本变成了
元素——一个指向追踪主机的 `preconnect`、一个 `meta refresh`、一条 referrer 策略——而这些
清理器一个都没看见过。它现在按框架将要用的方式解析，关闭脚本，并直接移除 `noscript` 以及
其他原始文本元素。

回复和转发还会把清理过的邮件粘进撰写编辑器，而编辑器是仪表盘自己文档的一部分，不是那个
框架：邮件里的一个 `<style>` 块会在读者书写时重新给整个页面上样式，还可能在上面铺一个假的
登录界面。引文现在在到达编辑器之前会丢掉 style、link、meta 和 id，而编辑器自己管住了自己的
绘制。

### SEC-23——IMAP 忽略了 `mail:write`（中，已修复）

仪表盘的每一个 mutation 都检查 `mail:write`；IMAP 路径上没有任何东西检查，所以一个角色只
允许读的用户，可以从邮件程序里加旗、移动、expunge、append 和删除文件夹。这个权限现在在
登录时和每次重新检查时读取；没有它，文件夹以只读打开，会写的命令拒绝执行。

### SEC-24——邮箱规则可以把一封邮件转发成环（中，已修复）

别名转发会加上 `Delivered-To`，这正是防止一封邮件被转发回来的办法；规则转发没有加，所以
两个互相转发的邮箱会把一封邮件永远传来传去，每次多一条 `Received`。规则转发现在会加上这个
头，而且一条规则不会把邮件转发到它已经投递过的地址，也不会转发已经穿过二十五台以上主机的
邮件。

### SEC-25——客户端输出里的终端控制字符（中，已修复）

`teanode mail list` 把主题行和发件人名字原样写到终端。终端服从控制字符，所以一封邮件可以
把光标上移并覆盖上面那一行——一封被拒收的邮件读起来就成了已投递——或者往剪贴板里塞一条命令。
现在每一个单元格、字段、错误，以及当标准输出是终端时的邮件正文，其中的这类字符都会显示为
它们的转义形式。输出到文件或管道时不变。

### SEC-26——向邮件服务器转发时，密码走在未经验证的 TLS 上（低，已修复）

一个 `mailserver` 类型、带用户名和密码的别名，是用机会式、不验证的 TLS 连接的，所以在那个
名字上应答的人就拿到了密码。中继路径是验证的；这一条在有密码时现在也一样，要求 STARTTLS
并对照配置的主机检查证书。

### SEC-27——登录的时间差指出了哪些地址有邮箱（低，已修复）

一个背后没有邮箱的地址，应用专用密码登录会被立刻拒绝；有邮箱的则在一次 bcrypt 之后才被拒绝。
现在每一次拒绝都要花一次 bcrypt，而且一个邮箱最多持有二十份应用专用密码，每一份都是登录时
多出的一次。开始一次 passkey 仪式——任何人都可以做，而且会保持五分钟——现在也计入登录限速器。
每个请求都要验证一份凭据的发信端点，计入提交限速器。

### SEC-28——改密码之后，其他会话仍然有效（低，已修复）

改密码，或者管理员重置密码，通常是因为别人也拿到了它，而那个人可能已经登录了。该账户的
其他每一个会话现在都会结束；发起这次改动的那个留着。

### SEC-29——客户端带着令牌跟随重定向，并且有一瞬间把配置档案写成所有人可读（低，已修复）

API 客户端会跟随重定向，而标准库在重定向到同一主机时会保留 `Authorization` 头，包括从
`https` 到 `http`。它现在把重定向当作它本来的样子——一个答复——报告出来。配置档案文件曾经
以默认权限创建、之后才改成私有；现在创建时就是私有的。登录页面提供的备用命令把令牌放在
命令行上，而 shell 的历史会留着它；现在它从终端读取令牌，不回显。

### SEC-30——修好的小事

- 到达时会移除指名本服务器的 `Authentication-Results` 头，这是 RFC 8601 §5 的要求；留下来的
  那个会坐在真正那个的上面，对下游的一切都是如此。
- 拒绝 `rsa-sha1` 签名，这是 RFC 8301 的要求。
- 一个 `_dmarc` 名字上，除策略之外还有别的 TXT 记录时，会拒收该域名的每一封邮件，因为记录
  被拼在了一起；现在只读 `v=DMARC1` 的记录，而多于一条就等于没有。
- 无法验证的 ARC 链曾以永久错误拒收邮件；现在它是一条失败的链，这也是告诉下一跳的说法，
  正如 RFC 8617 §5.2 所说。
- 签名的退信地址，其签名以常数时间比较。
- `safefetch` 拒绝 6to4、Teredo 和 NAT64 前缀，它们里面裹着一个 IPv4 地址。
- 垃圾邮件过滤器的头部扫描、头部分词和链接提取，都像它的正文扫描本来那样有了上限。
- 外出自动回复要求 `mail:send`，和规则转发一样。
- 每一个列表查询无论要多少行，都封顶在 1000 行。
- 一个已停用的账户即使到达了 GraphQL 处理器，也不再用它旧有的授权构造出一个 principal；
  中间件本来就已经拒绝它了，所以这一条是潜伏的。

### SEC-31——发布用校验和而不是签名来验证（中，未解决）

自升级通过 TLS 从 GitHub 下载一个发布，并对照旁边发布的 `SHA256SUMS` 检查它。这个校验和是
由构建这个二进制文件的同一个作业产生的，所以它证明的是字节完整抵达，关于是谁生产的它什么
也没说。任何能发布一个 release 的人——维护者的账户、发布令牌，或者发布工作流以可变标签引用的
第三方 action——都可以把一个恶意二进制文件交给每一台开着自动升级的服务器，而它会带着环境里的
数据库凭据执行它。修法是一把放在构建之外的签名密钥：在发布作业里为 `SHA256SUMS` 签名，把
公钥编进二进制文件，并拒绝没有有效签名的发布。这既是对代码的改动，也是对发布流程的改动，
留作单独一次改动。在那之前，工作流里的 action 应当固定到提交。

### SEC-32——compose 文件自带一个固定的数据库密码（低，未解决）

`deploy/docker-compose.yml` 设置了 `POSTGRES_PASSWORD: teanode` 并把数据库发布在
`127.0.0.1:5432` 上，所以宿主机上的任何账户都能读到服务器密钥和每一封存下来的邮件。本次
审查的信任模型已经把 PostgreSQL 放在运维者的网络之内；在一台专用主机上，那就是这台主机的
其他用户。修法是在 `config env` 里生成这个密码并从 `.env` 读取，而这是一项现有部署必须被
带着走一遍的改动，所以不在这里做。

### SEC-33——改名成控制台名字的账户就成了控制台（严重，已修复）

控制台——在服务器上带着服务器密钥运行的命令行——只靠用户名和一个账户区分开：一个带着
`(local)` 的请求被当作持有全部权限来处理，并且从不去查。v0.17.0 让一个人可以编辑自己的
账户，包括用户名，而没有任何东西保留那个名字。一个除了能登录之外没有任何权限的成员，可以
用 `username: "(local)"` 调用 `UpdateUser`；他的会话是按用户 id 索引的，从此每一个请求都
带着控制台的名字，而那能读每一个邮箱、改每一项设置、为任何账户签发 API 令牌——一次比改名
本身活得更久的接管。

这个名字现在在任何给账户命名的地方都被拒绝——`User.Validate`，数据库、命令行和身份提供方
的开户都要经过它，以及 API 自己的检查——而一个不知怎么带着这个名字的账户在登录时会被拒绝，
所以即使那一行存在也不会被相信。每一层都有断言。它是在发布之后的第二天、在对 v0.17.0 的
那一遍里发现的；自助服务的测试证明的是一个人可以改哪些*字段*，而不是哪些*值*。

### SEC-34——登录页面把一个查询参数写进了一条要粘贴的命令（中，已修复）

命令行客户端打开的那个登录页面，从 URL 里取配置档案的名字，并在浏览器联系不上客户端时，
提供一条 `teanode auth login --name <name> …` 命令供复制。没有任何东西检查这个名字，所以
一个构造过的链接——发给一位运维者，他按下 Authorize 并粘贴给他的东西——会在到达 shell 的
那一刻运行名字里的任何内容。页面现在只在名字是一个主机名或一个单词时才把它包含进去，而
客户端会拒绝任何别的名字作为 `--name`，所以一个正当的名字永远不会绊到它。

### SEC-35——伪造的 `List-Id` 借用了读者的「总是加载图片」（低，已修复）

v0.17.0 让读者可以一次性地说，某个邮件列表的图片可以不再询问就加载。这个列表是用它的
`List-Id` 识别的，而那是一个任何人都能写的头，所以一个猜中了读者信任哪些列表的陌生人，
就让自己的追踪图片被加载了——经由代理，所以没有地址泄露，但打开这件事和它的时刻泄露了，
而那正是这个询问要挡住的东西。这个长期答案现在只适用于通过了 DMARC 的邮件，也就是这个
列表的标志本来就遵循的规则；服务器执行它，列表自己的阅读器也执行它——后者曾经把这个答案
用在屏幕上的每一封邮件上。

### 同样未解决

- 一封投递的 DSN 可以被收到它的人重放：每一封都会改写这次投递的状态，而对于一封外发的
  原件，还会为发信人的别名目标创建一次新的退信投递。持有者是接收方服务器，所以这是有界的；
  一个「过了之后投递不再接受通知」的时间窗会关上它。
- `dns-01` 求解器把每一个已配置主机的质询记录都写进那一个托管区域，所以 `perDomain` 加上
  `dns-01`、再加上一个在那个区域之外的域名，会让服务器自己的订单失败。这是一个可用性
  bug，不是安全 bug。
- IMAP 的 `SEARCH TEXT` 每条命令都会从存储里读取并解析文件夹里的每一封邮件，而 `APPEND`
  会按邮件所带的 `From` 把它归档为外发邮件，该域名的审计者随后就会看到它。
- `PDF` 附件在仪表盘自己的源上内联打开。没有已知的浏览器会从 PDF 里运行脚本，所以这属于
  加固。

## 这一次验证过的控制

在第一次审查的清单之外，写出来是为了没有人重做这些工作：

- **DKIM**：拒绝 `l=`；拒绝小于 1024 位的 RSA；空的 `p=` 是错误而不是通过；`k=` 必须与
  `a=` 匹配；`x=` 被执行；`i=` 必须在 `d=` 之下；头的选择自下而上，被超额签名而不存在的
  头不贡献任何东西；一次验证错误本身绝不拒收一封邮件。
- **SPF**：每一个会解析的机制都计入十次查询的上限；多于一条记录、多于一个 `redirect=`、
  多于十个 MX 主机都是 `permerror`；`%{p}` 永不解析；宏的输出不能带 `/`。
- **DMARC**：组织域名取自公共后缀列表；只有记录来自上层时才应用 `sp=`；本服务器不*发送*
  报告，所以不涉及外部目的地验证；Go 的 XML 没有实体展开。
- **ARC**：判定不参考它，所以不需要可信封缄者列表；上限五十组。
- **IMAP**：每一个文件夹和条目都通过已登录的邮箱解析，所以别的邮箱的 UID 或名字找不到；
  `LOGINDISABLED` 和 `AUTHENTICATE` 都等待 TLS；literal 有上限；`SEARCH` 在 Go 里求值，
  所以没有客户端字符串到达 SQL。
- **Passkey 与单点登录**：仪式一次性并会过期；注册绑定到调用者；断言会对挑战、来源、
  RP ID、签名和用户句柄验证；state 和 nonce 被封缄并过期；身份只按 `(provider, subject)`
  关联，绝不按邮箱；返回路径限制为同站路径；身份提供方通过一个在拨号处就拒绝私有地址的
  客户端访问。
- **自升级**：仓库和端点编译在内；只走 HTTPS，重定向时不降级；只接受严格更新的版本；
  暂存的二进制文件以私有权限写入，执行前检查属主和模式；要求 `server:manage`；没有任何
  东西到达 shell。
- **存储**：标识符带有路径字符就拒绝；每一个都来自数据库的一行。
- **客户端**：环回监听在 `127.0.0.1`，随机端口，检查 nonce，令牌由 POST 送达，只回调一次，
  五分钟超时；打开浏览器不经过 shell；除非 `--insecure`（会声明出来）否则验证 TLS；密码
  读取时不回显；`mail download` 绝不覆盖。
- **部署**：非 root 镜像，只有 `NET_BIND_SERVICE`；没有 Docker socket；工作流权限最小化；
  没有 `pull_request_target`；不受信任的字段经由 `env` 传入而不是插值。
- **静态密钥**：`gitleaks` 扫过每一次提交，什么也没找到。
- **仪表盘依赖**：`npm audit --omit=dev` 什么也没找到。

## 这次审查没有做的

不是靠一致性测试套件。上面的发现是阅读所找到的；对 `mailparse`、`dkim` 和 `dmarc` 做一次
