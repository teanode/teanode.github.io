Model Context Protocol 是程序之间互相说明「我能做这些事，按名字叫它们」的那套约定。
TeaNode 在这套协议的两端都在：两个方向共用一种线上格式，除此之外几乎没有共同点。

**向外**，你的代理连到你已有的那些服务器上，它们的工具就成了它的工具。**向内**，
TeaNode 自己应答这套协议，所以你运行的一个写代码的工具、或者一个编辑器，可以用你代理的
那些工具，也可以用一句话向你的代理提问。

## 应答它：在你的编辑器里用你的工具

    POST /api/v1/mcp

每一个请求都自带令牌，请求之间什么都不保留，所以任何一端重启都不会丢东西。给一个程序令牌
有三种办法。

    # 把它指向这个地址，然后在浏览器里批准
    claude mcp add --transport http teanode https://mail.example.com/api/v1/mcp

    # 在你命令行已经登录的那台机器上
    claude mcp add teanode -- teanode agent mcp serve

    # 或者你自己交给它一个 API 令牌
    claude mcp add --transport http teanode \
        https://mail.example.com/api/v1/mcp \
        --header "Authorization: Bearer tnt_..."

第一种哪里都不用复制东西。没带令牌被拒之后，程序会被告知去哪里注册、把你送到哪里；你在仪表盘
上登录（如果还没登录的话），看清是哪个程序在要，然后允许它。它注册时不带密钥，因为一个装在
别人机器上的程序保不住密钥；它在取令牌时证明自己就是当初提出请求的那个程序。

它拿到的令牌比 API 令牌窄：只对代理的工具有效，GraphQL API 和其余一切都会拒绝它。它每次刷新
都会被换掉，所以这类令牌按程序列出，而不是跟你的 API 令牌列在一起。设置里的「应用」可以给
一个程序改名或者断开它，断开会吊销它持有的每一个令牌；`teanode app` 也一样。

有些托管的助手不自己注册，而是向你要一个客户端标识。那就为那个助手自己的回调地址注册一个。
必须正好是那个地址：批准只会被送到程序注册过的地址上。

第二种是一根管子，而不是第二套实现。`teanode agent mcp serve` 把每一条消息用你已经登录的
那个 profile 发到同一个端点上，所以服务器提供什么，它就提供什么。

第三种是给两样都不会的程序用的。一个 API 令牌带着它所属账号的全部权限，所以发不发它是运维者
的事，收好它是你的事。

程序通过代理的工具做过的事，在代理的「活动」页上，每一次调用的工具、每一个问过的问题，都记
在 `mcp` 这一类下面。

### 调用方会拿到什么

你的整份清单，按一轮对话同样的方式过滤：你的权限允许的，减去运维者关掉的，再加上你已经
连接的那些服务器的工具和运维者装的技能。一个不能读邮件的人不会被给到邮件搜索，因为那个
工具本来就不在他的清单里。每个工具都带着它的标注，只读还是破坏性，所以那个程序也能像代理
一样，分清看一眼和改一下。

这些都不会多给出令牌本来没允许的东西。在浏览器里批准的程序只能碰代理的工具；拿到 API 令牌
的程序，本来就能通过挨着这个端点的 GraphQL API，做那个账号的权限所允许的每一个操作。变的
是请求的形状，不是可以要求什么。

一次 `tools/call` 就是运行那个工具。它不会开一轮由模型来决定要不要运行的对话——你已经
知道自己要什么，中间再放一个模型会花钱、会多等几秒，而且每次答得还不一样。每一次调用都
以你的身份执行、以你的身份记账。

调用到达时就带着「已确认」。你的工具在运行之前会先问你，而这台服务器没有任何一张卡片能
够着你；你交给它的那份凭据，就是你确实同意了的意思。工具标成不可信的东西，在送回去之前
会被包起来，跟代理自己那一圈的做法一样——那个工具会把它交给它自己的模型，那个模型跟我们
的一样需要被提醒。

### 问代理，而不是驱使它

`teanode_ask` 接一句话形式的问题，返回你代理的回答，背后是它全部的家当和它关于你的记忆。
一个本来要编排六次调用的工具，问一次就够了。

它的时限取决于调用方愿意等多久，而不是取决于一轮要花多久。多数工具给一次调用大约一分钟。
55 秒之后，这一个会把到那时为止说过的话返回，并说出这场对话叫什么；那一轮继续跑，带着
那场对话、不带问题再调一次，就能把剩下的取回来。中途已经跑完的那一轮也会被交回来，并把
它说过的话重播一遍，所以晚一点回来也还是听得到答案。一次运行结束十分钟之后，答案就只在
那场对话里了。

一轮如果停下来举起一张确认卡片，是没法从这类工具里回答的。回答会说明这一点，并说那张卡片
正在仪表盘里等着，而不是看起来像一个莫名其妙停住的答案。

### 有两个工具没被放进来

`ask_user` 的存在，是为了把一个问题摆到正在看着的人面前。一次调用的另一端确实有人，但他
看的是自己那个工具的界面，而这台服务器画不到那上面去。伸手去够它的工具会拿到一个说明情况
的错误，而不是一个猜出来的答案。

`tool_search` 的存在，是为了在需要之前别把一长串清单塞进模型的请求里。这类工具会把清单
列一次然后留着，所以给它清单本身反而更好。

## 连出去：你的代理会用的那些服务器

另一个方向。运维者声明一台服务器——名字、地址，以及人们怎么在上面鉴权：不用鉴权、一份共享
凭据、各人自己的，或者 OAuth。然后你接上自己的凭据，或者对使用 OAuth 的服务器在浏览器里
授权。凭据在存下来之前会用服务器密钥封起来。

    teanode agent mcp list
    teanode agent mcp connect tracker --credential -
    teanode agent mcp disconnect tracker

回来的东西按服务器的名字加上命名空间，然后并进你的清单。每台服务器的工具列表会保留五分钟，
连着三次失败就把这台服务器的工具撤下来，直到下一个周期——这样一个服务挂了，不会把你代理的
整副家当一起带走。

每个工具都带着它的服务器给的标注，比如只读或者破坏性。只读的工具不问就运行，运维者列成只读
的也一样；破坏性的会问。其余每一次调用，由快速模型来判断，只在它代表你对别人做事、动钱、下单
或撤单、或者删东西的时候才问。看一眼账户也要弹一张卡片，会把人教成不读就点同意，那比没有卡片
还糟。这类服务器返回的一切都是数据。它从不下达指令。

有些服务只把授权送回一个回环地址，那是为你自己机器上的程序准备的方式。这样声明的服务器会改由
你接入的那台电脑来授权：在那台电脑的浏览器里完成它，仪表盘就会把连接接好。

## 让它指向自己

没有什么拦得住运维者把这台服务器自己的端点声明成代理的一台已连接服务器，那会让代理拿到
一份带命名空间的、它自己的清单副本，而一次调用会原路绕回来。握手会拒绝一个自称是 TeaNode
的客户端，而我们自己的客户端正是这么自称的；并且 `teanode_ask` 从来不在代理自己的清单里，
所以就算绕过了第一道关，也没法顺着它递归下去。
